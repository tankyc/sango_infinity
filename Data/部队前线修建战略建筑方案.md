## 二、总体设计（四层）

```
┌─ A. 资源层 ── 部队带多少钱、钱从哪来
│    复用 Troop.gold；出征拨款 + 战利品 + 补给队送钱
│
├─ B. 决策层 ── 谁决定"去前线建"
│    新增 ForceAI 战区扫描 + 派遣工程队（或复用 CityAI 扩展）
│
├─ C. 选址层 ── 建在哪个格子（★ 核心）
│    前线价值评分：己方密集度 / 敌我距离带 / 战略要道 / 可建性
│
└─ D. 选型层 ── 建什么建筑
     按战场态势（气力低→军乐台，缺粮→阵/砦，攻势→太鼓台，要道→箭楼）
```

### B. 决策层：三种架构可选

| 方案 | 做法 | 改动量 | 特点 |
|---|---|---|---|
| **B1 城池驱动（就近扩建）** | 把 `AIBuildMilitaryBuilding` 的选址范围从 `city.areaCellList` 扩到"辖区 **+ 前线缓冲带**" | ★ 小 | 复现成本最低，但仍是"城建思维"，部队只是跑腿，最远仍是城郊 |
| **B2 战区驱动（专职工程队）** | 新增 `ForceAI` 层决策：扫描全势力前线 → 找出值得建的点 → 从最近城池派**工程队**携款前往 | ★★★ 中大 | **真正的前线行为**，可跨城协同、可连建，最贴合需求 |
| **B3 随军增筑（就地建造）** | 让满足条件的**前线作战部队**自己就地建（有闲钱 + 处前线 + 附近有合适空位 + 建筑有价值） | ★★ 中 | 响应最快、最自然，但可能干扰主线任务；资金来自战利品 |

> 可组合：**B2 主力 + B3 补充** 是最完整的形态。

### C. 选址层：前线价值评分（核心）

对每个候选空格 `cell` 打分（全部权重可配）：

```
score = 覆盖收益 − 风险 − 建造成本惩罚
```

| 维度 | 计算方式 | 权重字段建议 |
|---|---|---|
| **己方覆盖** | `cell` 周围 `coverRange` 格内己方部队的**兵力总和**（建筑范围通常 2~3 格，取 `bound+1`） | `frontCoverWeight` |
| **敌我距离带** | 到最近敌人的距离落在 `[safeMin, safeMax]` 时给满分，过近（会被拆）或过远（用不上）递减 | `frontIdealEnemyDistMin/Max` |
| **战略要道** | 邻近关(@2)/港(@3)/城池，或地形为通道（可复用 `Cell` 的邻接度或 `moveAble` 计数） | `frontChokeWeight` |
| **覆盖稀缺度** | 附近 `buildingSpace` 格内**没有任何己方同类建筑** → 加分；已有 → 直接跳过 | 硬性规则 |
| **威胁惩罚** | `cell` 周围 `threatRange` 格内敌方兵力越高越危险 | `frontThreatWeight` |
| **可建性** | `buildingType.CanBuildToHere(cell)` 为 false → **直接排除** | 硬性规则 |
| **在己方控制区** | 可选：`cell` 距己方城池/部队越近越安全（原代码无领地校验） | — |

### D. 选型层：态势 → 建筑映射

把 G2 的"纯随机"换成"**态势驱动 + 权重随机**"：

| 战场特征（判定条件） | 优先建筑 | 理由 |
|---|---|---|
| 覆盖范围内己方**平均气力低**（< 阈值） | **军乐台(13)** | 气力是战力核心，鏖战必备 |
| 覆盖范围内己方**粮草紧张**（`IsWithOutFood()==1` 占比高） | **阵(4) / 砦(5) / 城塞(6)** | 粮耗 -40%~-60%，性价比极高 |
| 我方处于**攻势**（局部兵力占比 ≥ 优势档） | **太鼓台(12)** | 攻击 +10 直接提升推线效率 |
| 目标是**扼守要道**（邻近关/港/城池，敌方必经） | **箭楼(7) / 连弩楼(8) / 投石台(11)** | 自动输出，无需驻军 |
| 与敌**长期对峙**（双方兵力接近且持续多回合） | **砦(5) / 城塞(6)** | 防御 + 省粮，最耐耗 |

> 复用已有基础设施：`BattleSituation.EvaluateBalance` / `TroopBattleTier` 可直接提供"局部兵力占比"，判断攻势 / 劣势。

## 四、关键设计细节

### 4.1 为什么 P0 改动量不大

现有链路已完整：

```
CityAI.AIBuildMilitaryBuilding
  ├─ 选 dest（★ 只改这里：从 areaCellList → 前线评分）
  ├─ 选 buildingType（★ 只改这里：随机 → 态势驱动）
  ├─ city.gold -= carrayGold
  └─ troop.gold = carrayGold;  SetMission(TroopBuildBuilding, typeId)
        ↓
TroopBuildBuilding.DoAI → MoveTo(FinalCell) → troop.BuildBuilding(cell, type)
        ↓
TroopBuildBuildingEvent → City.BuildBuilding → builder.gold -= cost
```

**只需替换"选址"与"选型"两块**，其余不动。

### 4.2 `TroopBuildBuilding` 的连建改造要点

现状（`TroopBuildBuilding.cs:41-49`）：

```csharp
if (IsMissionComplete)
{
    if (Troop.mBelongCity.IsSameForce(Troop))
        Troop.SetMission(MissionType.TroopReturnCity, Troop.mBelongCity.Id); // ← 立即回城
    else
        Troop.SetMission(MissionType.TroopOccupyCity, TargetCity.Id);
    Troop.NeedPrepareMission();
    return;
}
```

改造思路：建完后**先找下一个建点**（复用 `missionParams1/2` 记录原任务，参考 `TroopAskSupply` 的写法），无目标或钱不足再回城。

## 七、风险与注意事项

| 风险 | 说明 | 缓解 |
|---|---|---|
| **AI 建造过多拖垮经济** | 军乐台 800、城塞 1200，频繁建造会吃光金库 | `frontBuildMaxPerForce/PerCity` + `frontBuildMinCityGold` 双重限流 |
| **建筑被迅速拆除** | 建在敌人的打击范围内等于送钱 | `frontBuildSafeMinDist` 硬性排除过近点 |
| **与主线任务冲突** | 工程队占用兵力，影响攻城/防守 | 工程队由城池单独编成，不抽调作战部队；兵力阈值控制 |
| **重复建造浪费** | 同一片区域建多个同类建筑 | 硬性规则：`buildingSpace` 内已有同类则跳过 |
| **性能** | 全势力扫描 + 每格评分，格子数可能很大 | 只在"城池出兵决策时"扫描一次；候选格先按 `CanBuild`/`IsEmpty` 粗筛再评分；`frontBuildSearchRange` 限制 |
| **存档兼容** | 新增 `[JsonProperty]` 字段 | 缺字段时反序列化取默认值，无影响 |
| **改变现有 AI 行为** | 选址/选型改动会让 AI 表现变化 | 提供 `useFrontBuilding=false` 一键回退到旧逻辑 |

## 二、建址评分公式

```
score = 覆盖收益  +  要道加成  +  距离带得分  −  威胁扣分

覆盖收益  = min(覆盖兵力 / 10000, 1) × 100 × frontCoverWeight
要道加成  = hasChoke ? frontChokeWeight : 0
距离带    = (100 − min(100, 偏离格数 × 20)) × frontDistanceWeight
威胁扣分  = min(威胁兵力 / 20000, 1) × 100 × frontThreatWeight
```

**硬性排除**：地形不可建 / 已有部队或建筑 / 内城格 / 间距不足 / 距敌 < `frontBuildSafeMinDist` / 覆盖兵力 < `frontBuildMinCoverTroops` / `score < frontBuildSiteMinScore`。

## 三、选型优先级（替代原「纯随机」）

| 顺序 | 条件 | 选中建筑 |
|---|---|---|
| 1 | 覆盖范围内己方平均气力 < `frontBuildLowMoralePercent` | **军乐台(13)** |
| 2 | 缺粮部队占比 ≥ `frontBuildLowFoodPercent` | **阵(4) → 砦(5) → 城塞(6)** |
| 3 | 邻近要道且敌人 ≤ `frontBuildThreatRange` | **箭楼(7) → 连弩楼(8) → 投石台(11)** |
| 4 | 我方兵力占比 ≥ 优势档 | **太鼓台(12)** |
| 5 | 兜底 | `frontBuildPreferredTypes` 序列 → 任取可建类型 |

## 四、资金流转（双来源）

```
城池金库 ──(出征拨款)──→ 工程队 troop.gold ──(建造)──→ BuildingType.cost 扣除
   ↑                            ↑
   │                            └──(补给队转运)── supplyTransferGoldPercent
   └──(击破敌军掠夺)── GainTargetResource（既有机制，无需改动）
```

- 工程队携款：`frontBuildBudget`，为 0 时按 `造价 × frontBuildGoldCostPercent%` 推算（支持连建）
- 作战部队携款：`troopCarryGold`，受 `troopCarryGoldPerTroops` 与城池余额双重限制
- 补给队运钱：仅当友军 `gold < supplyNeedGoldThreshold` 时补足，并保留自身最低资金
- 资金耗尽的工程队自动回城补充

## 五、行为链路

```
【B2 专职工程队】
CityAI.AIBuilding
  └─ AIBuildMilitaryBuilding
       └─ TryBuildFrontBuilding          ← 扫描前线，评分选点
            └─ SelectFrontBuildingType   ← 态势选型
                 └─ DispatchBuildingTroop ← 建队 + 携款 + role=Engineer
                      └─ SetMission(TroopBuildBuilding, typeId)
                           └─ TroopBuildBuilding.DoAI
                                ├─ 抵达 → BuildBuilding
                                └─ 完工 → TryFindNextSite → 有址则连建 / 无址则回城

【B3 随军增筑】
Troop.AIPrepare（所有撤退判定之后）
  └─ TryBuildFieldBuilding
       ├─ 记录原任务到 fieldBuildReturnMission / fieldBuildReturnTarget
       └─ 转 TroopBuildBuilding
            └─ 完工 → 恢复原任务，重返战线
```

## 七、顺带修复的既有缺陷

1. **`BuildingImproveTroopAttack` 的 improveKey**（已修）
   原为 `"BuildingImproveTroopDefence"`，导致太鼓台与阵/砦/城塞写入 `troop.buildingImproveMap` 的同一个键而互相覆盖 —— 表现为攻击加成时有时无甚至变负。已改为 `"BuildingImproveTroopAttack"`。
2. **`CityAI` 副将赋值笔误**（已修）
   `if (builders.Length > 2) troop.Member1 = builders[2];` 会把第二名副将写到 `Member1`，覆盖掉第一副将。已改为 `Member2`。
3. **`TroopBuildBuilding` 重复发起建造**（已修）
   建筑处于施工中时 `IsMissionComplete` 为 false，`DoAI` 每回合都会再调 `BuildBuilding`。已加"目标格已有己方建筑则跳过"。
4. **`TroopBuildBuilding` 目标格不更新**（已修）
   原先 `if (TargetCell == null) TargetCell = troop.missionTargetCell;` 只在 null 时赋值，改派新建址后仍围着旧目标打转。已改为每次核对。
5. **`TroopBuildBuilding` 回城分支未判空**（已修）
   `Troop.mBelongCity.IsSameForce(...)` 与 `TargetCity.Id` 均可能空引用。
