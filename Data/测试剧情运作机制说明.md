## 0. 一句话结论

**项目里同时存在两套互不知情的"剧情/事件"体系**：

| | 旧体系 | 新体系 |
| --- | --- | --- |
| 名字 | `RenderEvent` | 剧本事件系统（`Sango.Core.Event`） |
| 演出逻辑在哪 | **硬编码在 C# 类里** | **数据驱动**（JSON） |
| 队列 | `RenderEvent.eventQueue`（表现层，可跨回合阻塞） | `Scenario.eventsSet` → 逐个交给 `EventRunner` |
| 代表 | `CityPersonSearchingEvent` / `CityRecruitPersonEvent` | `EventRunner` + `EventDefinition` |
| 数据 | 无（代码即内容） | `Data/ScenarioEvent/*.json` |

它们**共用同一个 `GameDialog` 对话队列**，都往**同一个 `GameSystem` 系统栈** push，
而且**旧体系会在自己的演出中途抛出 hook 去触发新体系**（这是最要命的一条，见 §5.3）。

那 3 个曾被认为属于旧体系的 JSON（`1_回合开始军师慰问` / `10_搜索失败` / `11_搜索到人才`）
**全项目没有任何旧代码读它们** —— 旧体系的行为是硬编码的，那批 JSON 一直是死数据。
现在它们只被新体系的 `EventDatabase` 消费。

两套体系的分工是"错位"的：

- **旧体系在"演出之前就持有指令"**：玩家点探索 → 指令入队 → 演出时才结算（§2.4）

所以它们天然会在**同一时刻**想去开对话框，这就是冲突的根源。

## 2. 旧体系：`RenderEvent`

### 2.1 播放器

**文件**：`Game/Render/RenderEvent/RenderEvent.cs`
**类型**：`RenderEvent : Singleton<RenderEvent>`

内部结构：

| 成员 | 作用 |
| --- | --- |
| `List<IRenderEventBase> eventQueue` | **主队列**：串行，一次只播一个 |
| `List<IRenderEventBase> dependsEventQueue` | 依赖队列：**并行**，每帧对所有项 `Enter`/`Update` |
| `IRenderEventBase CurEvent` | 当前主队列项 |
| `Dictionary<string, Stack<IRenderEventBase>> eventPool` | 按类型复用对象池 |
| `int queueHead` | 主队列读取游标（避免每项一次 `RemoveAt(0)` 的 O(n²) 搬移） |

关键入口：

```csharp
public T Create<T>() where T : IRenderEventBase, new()   // 从池里取，取不到才 new
public void Add(IRenderEventBase renderEvent)             // MarkDepends ? 依赖队列 : 主队列
public void Reset()                                       // 两个队列 + 对象池 + CurEvent + 游标 全清
public bool Update(Scenario scenario, float deltaTime)     // 返回 false = 还在演出
```

### 2.2 驱动方式与"挡住回合"

```csharp
// Scenario.Run()  Scenario.cs:1456
if (!RenderEvent.Instance.Update(this, Time.deltaTime))
    return;                                   // ← 演出未结束，本帧不推进回合
```

也就是说：**主队列里只要有一项没播完，整个回合推进就停住**。
这不是"演出插播"，而是"演出是回合的一部分"。

### 2.3 `IRenderEventBase` 契约

| 成员 | 语义 |
| --- | --- |
| `bool IsInited { get; set; }` | 是否已 `Enter`。播放器据此避免重复 Enter |
| `bool IsDone { get; set; }` | **本项结束**。由事件自己在回调里置 `true` |
| `bool IsVisible()` | 默认 true。**全项目没有任何地方调用它** —— 是死代码，子类里的实现只是"语义备注" |
| `bool MarkDepends { get; set; }` | 决定进主队列还是依赖队列 |
| `bool Update(Scenario, float)` | 默认 `return IsDone` |
| `void Enter(Scenario)` / `Exit(Scenario)` | 空实现，子类重写 |

三种结束方式：

1. 主队列项：`Update()` 返回 `IsDone` → 事件自己在对话框回调里 `IsDone = true`
2. 依赖队列项：`Update()` 返回 true → **播放器代设** `IsDone = true` 并 `Exit`
3. 完全不设 → 该项永久卡住，整个回合推进永久停住（最常见的"卡死"原因）

`RenderEvent.Update` 的主循环（`RenderEvent.cs:113-130`）：

```csharp
while (queueHead < eventQueue.Count)
{
    CurEvent = eventQueue[queueHead];
    if (!CurEvent.IsInited) { CurEvent.IsInited = true; CurEvent.Enter(scenario); }
    if (!CurEvent.Update(scenario, deltaTime))
        return false;                 // 未完成：游标留在原地，下一帧继续
    CurEvent.Exit(scenario);
    CurEvent = null;
    queueHead++;
}
```

### 2.4 ⚠ 关键性质：**入队时不结算，`Enter` 时才结算**

旧体系最反直觉的一点：玩家点指令的那一刻**不产生任何数值结算**，
只把"要演的戏"排进队列；真正的结算发生在**演出开始的那一帧**。

以"探索人才"为例（这是本轮测试最相关的一条）：

```csharp
// ① 玩家点"人事 / 探索人才"：只入队，不结算

 └─ City.JobSearching(person[])            Game/Object/City/City.cs:3389
     └─ RenderEvent.Instance.Create<CityPersonSearchingEvent>() + Add()   City.cs:3396-3398

// ② 下一帧（或几帧后），演出开始：此刻才结算

         │   └─ Person.ActionOver setter             Person/Person.cs:526-542
```

`City.DoJobSearching` 的返回值语义（`City.cs:3408`）：

| 返回值 | 含义 |
| --- | --- |
| `0` | 找到人才（`out target` 有值） |
| `> 0` | 找到资金，数值即金额 |
| `-1` | 什么也没找到 |

这也解释了为什么旧代码里到处是 `rs < 0` / `rs == 0` / `rs > 0` 三分支。

### 2.5 旧体系怎么用对话框

**不是一次性排进队列，而是嵌套回调**：

```csharp
// CityPersonSearchingEvent.cs:49-85（简化）
GameDialog.Instance.Open(ClickPersonSay, "搜索结果，发现了名为X的武将。", () =>
{
    PersonRecruit.Start(person, target, 0, 1, x =>
    {
        if (x.result == 1)
            Open(ClickPersonSay, "成功招募了X", () =>
                Open(ClickPersonSay, "X愿为主公献犬马之劳", () => IsDone = true, target),
                person);
        ...
    });
}, person);
```

`GameDialog` 的机制：

- `Open(...)` → `Enqueue(...)`：把 `DialogData` 追加到 `dialogDatas`，然后 `TryAdvance()`
- `TryAdvance()`：`hasCurrent` 为真就**直接返回**（已有一条在占位，等它）
- `OnWindowClosed(seq, sure, invokeAction, allowAdvance)` 是**唯一**关闭入口：校验 `seq` → 清当前 → 执行回调 → （可推进时）`finally TryAdvance()` 继续下一条

所以虽然队列是 FIFO，但被 `hasCurrent` **串行化** —— 嵌套 `Open` 只是把下一条追加到队尾。

`PersonRecruit` 系统（`Game/System/Person/PersonRecruit.cs`）：

```csharp
public void Start(Person recruitor, Person target, int recruitType, int tryLimit, Action<PersonRecruit> doneAction)
```

- `[GameSystem]`，会 `Push()` 到系统栈，开 `window_person_recruit_info`
- 结果走 `result`：`1` 成功 / `0` 失败 / `2` 释放 / `3` 斩首或收押 / `-1` 取消

## 3. 新体系：`Game/Event/`

### 3.1 组件

| 文件 | 职责 |
| --- | --- |
| `EventDatabase.cs` | 三源加载 JSON（内置 / CustomEdit / Mod）+ `Kind` 索引 + 年份二级裁剪 |
| `ScenarioEventManager.cs` | `[GameSystem]` 应用级单例。订阅 24 个 `GameEvent` hook；10 道闸门；定时队列 |
| `EventSlotResolver.cs` | 把角色槽声明解析成实际对象（`PlayerForce` / `ForceBestPerson` / `TroopOfPerson` …） |
| `EventConditionEvaluator.cs` + `EventConditions.cs` | 条件树求值（复用既有 `Condition` 体系） |
| `EventRunner.cs` + `EventRunnerOps.cs` | `[GameSystem]` 状态机 + 17 条演出指令 |
| `EventEffects*.cs` | 24 种世界状态效果 |

### 3.2 一次触发的 10 道闸门

顺序按"开销升序 + 确定性优先"排列（`ScenarioEventManager.TryFireEvent`）：

```
① 启用 → ② 触发次数(Once/MaxFireCount) → ③ 冷却(CooldownTurns)
→ ④ 年份索引(EarliestYear/LatestYear)  → ⑤ 作用域(Scope)
→ ⑥ 剧本过滤(ScenarioFilter)           → ⑦ 密度(Level=Critical 免限)
→ ⑧ 槽位绑定(失败即放弃，不改世界状态)  → ⑨ 条件树
→ ⑩ 触发概率(Chance)                    ← 放最后，避免白白消耗随机数导致读档重放不一致
```

一次 hook **只播一个事件**（优先级最高者），其余留到下回合 —— 演出独占输入与对话框。

### 3.3 播出

```
EventRunner.Play(def, ctx, onFinished)
  → Push() 入系统栈（此后每帧由 GameSystemManager.Update 驱动）
  → Step()：循环执行同步指令，遇到"需要等待"的指令就停下
       Talk / TalkWindow / Message  → GameDialog.OpenTalk(...) → waiting = true
       Choice                       → PlayerChoice.Start(...)  → PlayerChoice 入栈，waiting = true
       Duel                         → DuelChallengeFlow.Request(..., Source.GameEvent, options)
                                      → 每帧轮询 DuelManager.IsDueling 判断结束
       Effect / SetFlag / Branch / Jump / Label / Schedule / SetVar / SkipAll / Parallel → 同步执行
       End                          → Finish()
  → Finish() 用 Back(this) 精确弹自己（不弹栈顶，避免误弹别人）
```

护栏：`Step()` 有**重入锁**（防对话同步回调嵌套）与**单帧指令上限 256**（防 Jump 成环卡死整帧）。

### 3.4 时间范围的三种机制（**容易混，务必分清**）

"事件在什么时候生效"在这个系统里有**三套语义完全不同**的机制：

| 层 | 配置位置 | 比的是 | 用途 | 落在哪一步 |
| --- | --- | --- | --- | --- |
| ① **时间索引** | `Trigger.EarliestYear` / `LatestYear` | 游戏**当前**年份 `Info.year`（会推进） | "这个大事件只在该时期存在"；同时是性能索引 | 闸门第 ③ 步 `EventTriggerDef.MatchYear` |
| ② **剧本过滤** | `ScenarioFilter.Mode="YearRange"` + `YearMin`/`YearMax` | 剧本**开局**年份（固定不变） | "这个事件只属于 200 年开局的剧本" | 闸门第 ⑤ 步 `EventDatabase.MatchScenarioFilter`，用 `ScenarioEventManager.ScenarioStartYear` |
| ③ **条件树日期条件** | `Conditions` 里的 `TimeRange` / `DateCheck` / `ScenarioYearCheck` | 当前 年 / 月 / 日 | 精确到月或日的时机 | 条件求值 |

> ① 与 ② 的差别最容易被忽略：
> ① 比的是"游戏跑到哪一年了"，② 比的是"这一局是从哪一年开局的"。
> 官渡之战只该出现在 200 年开局的剧本里 → 用 ②；
> 官渡之战只该在 200~208 年间发生 → 用 ①。

#### 时间换算（配置时必须知道）

`Scenario.IncreaseDate()`：`Info.day += 10`；`day > 30` 才进月；`month > 12` 才进年。因此：

- **1 回合 = 10 天**
- **1 月 = 3 回合**
- **1 年 = 36 回合**

所以 `EarliestYear: 200, LatestYear: 208` 其实是 **288 个回合**的跨度 —— 很粗的锚点。
要精确到月，必须叠加条件树里的 `TimeRange`。

#### 三个日期条件的参数

| 条件 | 参数 | 语义 |
| --- | --- | --- |
| `TimeRange` | `YearMin` / `YearMax` / `MonthMin` / `MonthMax` | 区间；`0` 或负数表示该维度不限 |
| `DateCheck` | `Year` / `Month` / `Day` | 精确值；`0` 表示不限 |
| `ScenarioYearCheck` | `Min` / `Max` | **剧本开局年份**区间（⚠ 曾误读当前年份，已修，见 §7.5） |

#### 配置示例

**只在该时期可能发生**（建议索引与条件双写：索引管性能，条件管语义）：

```json
"Trigger": {
  "Kind": "TurnStart",
  "EarliestYear": 200,
  "LatestYear": 208,
  "Once": true
},
"Conditions": {
  "Type": "and",
  "Children": [
    { "Type": "TimeRange", "Params": { "YearMin": 200, "YearMax": 208 } }
  ]
}
```

**只在每年冬春发生**：

```json
{ "Type": "TimeRange", "Params": { "MonthMin": 1, "MonthMax": 3 } }
```

**只在 208 年 10 月发生**：

```json
{ "Type": "DateCheck", "Params": { "Year": 208, "Month": 10 } }
```

**只属于"200 年开局"的剧本**（游戏推进到 220 年也照样适用，因为它比的是开局年份）：

```json
"ScenarioFilter": { "Mode": "YearRange", "YearMin": 200, "YearMax": 200 }
```

**条件满足后再憋 N 回合才演**（事件余波、伏笔回收）：

```json
"Trigger": { "DelayTurns": 12 }
```

`DelayTurns` 走的是定时队列（`Scenario.ScheduledEvents`），因此**随存档持久化、跨读档不丢**。
登记时用**负数** `SourceEventId` 与事件里的 `Op: Schedule`（正数）区分开（两者语义不同：
一个是"延迟自己"，一个是"安排别人"）。到达触发回合时会**重新求值一遍条件**，
不满足就不播 —— 语义上等价于"到那时局势已变，算了"。

### 3.5 图文展示的三种形态

| 形态 | 现状 | 说明 |
| --- | --- | --- |
| ① **人物立绘** | ✅ **已经在用** | `Talk` 指令填了 `Slot`，说话人的大立绘就出现在 `window_dialog4`；取 `Assets/Face/{headIconID}_1` |
| ② **表情切换** | ❌ **资源不存在** | 每个武将只有 `_1`（大立绘，均 13KB）/ `_2`（小头像，均 2.5KB），**没有表情变体**；要做需美术先出素材 |
| ③ **全屏插图 / 事件 CG** | ✅ **指令已实现**（待美术出图 + 做 prefab） | `Op: Picture` / `Op: PictureClose` |

> `_1` / `_2` 的语义（`CardDuelView` 注释里写明的）：`1` = 大立绘（对话框用），`2` = 小头像（武将条用）。
> 它**不是**"表情" —— 引擎侧没有任何表情资源可按。

#### `Op: Picture` 的用法

```json
{ "Op": "Picture", "Params": {
    "Image": "taoyuan",
    "Title": "桃园结义",
    "Text": "{:ActionPerson}、{:TargetPerson}、{:Slot3} 三人在桃园结为异姓兄弟。",
    "MinSeconds": 3.0,
    "PauseBgm": true
} },
{ "Op": "Talk", "Params": { ... } }
```

| 参数 | 说明 |
| --- | --- |
| `Image` | CG 资源名，**可省扩展名**（如 `"taoyuan"`），也可写完整相对路径 |
| `Title` / `Text` | 标题与正文，支持 `{:槽位Key}` 占位符 |
| `MinSeconds` | 最少展示秒数；`0` = 用入场动画时长；都没有则立即可关 |
| `PauseBgm` | 展示期间暂停 BGM，关闭时自动恢复 |

**行为**：铺满屏幕展示 → 等到 `MinSeconds` 后才**允许**关闭 → 玩家点击关闭 → 事件继续下一句。
与 `Talk` 一样是**阻塞**的，且回合推进被 `Scenario.Run` 的 `IsPlayingNow` 挡住。

`Op: PictureClose` 用于分支里"演到一半强制收场"（正常情况玩家点击会自行关闭）。

#### 容错设计（**绝不会把玩家卡死**）

| 情况 | 行为 |
| --- | --- |
| `Image` 指向的资源不存在 | 只记 `Log.Warning`，**降级为只显示文字**，事件照常往下走 |
| 窗口 prefab 还没做 | `Window.Open` 返回无效 → 记警告并**跳过**，不进入等待 |
| 参数缺失（`EventPictureArgs` 为空） | 放开 `canClose`，玩家点一下就能过 |
| 图、标题、正文**全是空** | 直接允许关闭，不让玩家对着空屏等 |

#### 与旧体系的关系

`window_force_destroy` 的驱动者 `ForceFallCompleteEvent` 是 **`RenderEventBase`（旧体系）**，
但 `Op: Picture` **不走 RenderEvent 队列** —— 由 `EventRunner` 自己开窗、自己等
（`UGUIWindow.OnCloseAction`），回合推进靠 `Scenario.Run` 的 `IsPlayingNow` 挡住。
这样两套体系在**窗口与队列上都不交叉**，避免重演上个阶段修掉的那类冲突。

> 一个必须注意的重入细节：`UGUIWindow.Close()` 的执行顺序是
> `SetActive(false)` → `OnClose()`（这里会触发 `OnCloseAction`）→ `IsOpen = false`。
> 如果在 `OnCloseAction` 里**同步**续播并又打开了同一个窗口实例（窗口是复用的），
> 最后那句 `IsOpen = false` 会把新打开的状态覆盖掉。
> 因此 `EventRunner` 只在回调里记一个标记，**推迟到下一帧的 `Update()` 才续播**。

### 3.6 总开关

**剧本参数 → 剧本事件 → 「启用剧本事件系统」**
（`ScenarioVariables.eventSystemEnabled`，默认开，随存档持久化）。

两个参数面板 —— 开局前的 `window_scenario_variables` 与游戏内的
`window_scenario_variables_ingame` —— **共用同一个 `UIScenarioVariables` 类**，
所以开关只需登记一次（在 `RefreshSetting()` 里 `AddToggleItem`），**两处都会出现**。

关掉后的行为：

| 项 | 关掉后 |
| --- | --- |
| 条件求值 | ❌ 完全不评估 —— 连条件树都不求值，零开销 |
| 定时事件队列 | ❌ 不推进；**待办项保留**，重新打开后按回合逐条补播（每回合只成功播一条，不会一次性连播二十个） |
| 被演出占用而暂缓的触发 | ❌ 不重试 |
| **正在播的那一个事件** | ✅ **照常播完** |
| 调试面板的强制触发（`FireEventNow`） | ✅ 不受影响 —— 那是显式意图，不是自动触发 |

「正在播的照常播完」是刻意的：中途掐断会留下半开的窗口与对话框，反而要写一堆清理逻辑；
而且玩家去关开关时，通常正是被某个事件打断的时候。

**实现位置**：

| 位置 | 覆盖范围 |
| --- | --- |
| `ScenarioEventManager.Enabled` | 读 `Scenario.Cur.Variables.eventSystemEnabled` |
| `OnTurnStart` | 定时队列 + 暂缓重试 + 每回合求值 |
| `EvaluateKind` | **所有 hook 驱动的触发**（它们都从这里进） |
| `TryFireEvent` | 兜底，覆盖绕过 `EvaluateKind` 的直接调用 |

> 开关状态**变化时**会打印一条中文日志（`剧本事件系统：已关闭…`）。
> 「事件怎么突然不弹了」这类问题，这条日志往往就是答案。

## 5. ⚠ 两套体系的交叉点（测试前必读）

### 5.1 C1：共用 `GameDialog` 的同一个队列

两个体系都往 `GameDialog.dialogDatas` 里投递，共用 `hasCurrent` / `TryAdvance` / `OnWindowClosed`：

| 体系 | 投递方式 |
| --- | --- |
| 旧 | `GameDialog.Instance.Open(style, content, sure, cancel, person)` |
| 新 | `GameDialog.Instance.OpenTalk(talks, endAction, style)` |

**后果**：窗口互相覆盖、`GameController.Instance.Enabled` 被反复开关。

**这已经造成过一次实际故障**：退出 Play 模式时报
`Cannot set the parent of the GameObject 'window_dialog4' while its new parent 'UIRoot' is being destroyed`，
并留下一个无人回收的窗口对象。成因是场景销毁时 `UIDialog.OnDestroy → GameDialog.OnWindowClosed → TryAdvance`
仍从队列里取待播对话去开新窗口。**队列里积压的对话越多，这个坑越容易踩到** —— 而两套体系同时投递正是积压的来源。

已修（`GameDialog.TryAdvance` 加 UI 根判活；`OnWindowClosed` 加 `allowAdvance`，销毁路径传 `false`）。

### 5.2 C2：都往 `GameSystem` 系统栈 push

| 体系 | push 点 | 开的窗口 |
| --- | --- | --- |
| 旧 | `PersonRecruit.Start` → `Push()`，`Game/System/Person/PersonRecruit.cs:31` | `window_person_recruit_info` |
| 旧 | `PlayerChoice.Start()` → `Push()`，来自 `TroopTransformChoiceEvent.cs:26`（RenderEvent 演出内） | `window_choice` |
| 新 | `EventRunner.Play` → `Push()` | — |
| 新 | `OpChoice` → `PlayerChoice.Start()` | `window_choice` |

> `PlayerChoice` 的真实调用点只有两处：`TroopTransformChoiceEvent.cs:26`（旧演出内）与
> `UI/Corps/UICorpsSetting.cs:268`（UI 面板）。`Troop.cs:2773` 那处已被注释掉、改走 RenderEvent。
> 所以新体系的 `OpChoice` 与旧演出会用**同一个** `PlayerChoice` 单例，这是 C2 里最实际的一条冲突。

`GameSystemManager` 只有**一个** `CurrentCommand`，后 push 的会盖住前者并触发 `OnExit`。
新的 `EventRunner.Finish` 用 `Back(this)` 精确弹自己（不会误弹别人），但旧体系不一定对称。

### 5.3 C3：旧体系在**演出中途**抛 hook 去触发新体系 —— ✅ 已修（2026-09-26）

`City.DoJobSearching` 是在 `CityPersonSearchingEvent.Enter()` **执行期间**被调用的，
它内部 `person.ActionOver = true` 会立刻抛 `GameEvent.OnPersonActionOver`。
而 2002 / 2003 / 1301 早期正是挂在这个 hook 上 —— 触发时机天然落在旧演出的正中间，
此刻旧的 `CityPersonSearchingEvent` 还停在 `Enter` 里等对话框回调（`IsDone` 未置位）。

而新体系的并发保护 `IsPlaying` **只挡自己**，完全不知道旧体系在播。后果是两套演出同时往
`GameDialog` 投递 → 窗口互相覆盖 → 退出时队列积压 → 触发 §5.1 的窗口泄漏。

**已按两条路同时修复。**

#### 修法一：让路闸门（`ScenarioEventManager.IsBlockedByOtherPresentation`）

任何一次求值前先判断别人是不是正占着演出：

| 判据 | 地位 | 理由 |
| --- | --- | --- |
| `GameDialog.Instance.HasCurrent` | **主** | 两套体系最终都落到同一个对话框队列上，这才是真正的冲突面 |
| `RenderEvent.Instance.HasPendingAfterCurrent` | 辅 | 旧体系当前这项演完后**后面还有戏**。刻意**不**看"有没有在播"—— 移动演出是"路径每格一个事件"，长距离行军期间一直非空闲，那样会把所有事件都推到下一回合 |

被挡下的触发**不丢弃，而是暂缓**：入 `deferredTriggers`（上限 32，超了明确告警），
在 `OnTurnStart`（上一回合所有演出都已结束的安静点）统一重试。
暂缓项连**结果码一起存** —— JobSettled 的 `JobResults` 过滤依赖它，丢了就退化成"任意结果都触发"。

定时队列同样让路，且必须在移除待办项**之前**拦住：
原流程是"先 `RemoveAt` 再尝试播放"，一旦播放失败待办项就永久丢了。

#### 修法二：给"探索结算完成"换一个干净的 hook

新增 `GameEvent.OnCityJobSearchingSettled(Person, City, int result, Person found)`，
在 `CityPersonSearchingEvent.Exit()`（演出**彻底结束**之后）抛出，并带上结果码。
同时新增触发时机 `EventTriggerKind.JobSettled` 与过滤字段 `Trigger.JobResults`。

三个事件已全部迁移：

| Id | 时机 | 结果码过滤 | 含义 |
| --- | --- | --- | --- |
| 2002 探索人才·无所得 | `JobSettled` | `[-1]` | 只在"一无所获"时播 |
| 2003 探索人才·寻得贤才 | `JobSettled` | `[0]` | 只在"发现人才"时播 |
| 1301 三顾茅庐 | `JobSettled` | 无 | 任一结果都推进一顾（理由见该文件 Description） |

> 2. 与 3. 以前**判不出成败**（`OnPersonActionOver` 不带结果）；现在靠结果码可以精确区分了。

#### 顺带修掉的第三个洞：事件演出原本**没有**挡住回合推进

早期 `EventRunner` 只靠 `GameDialog` 把 `GameController.Enabled` 置 false 来挡输入，
但 `Scenario.Run()` **照跑** —— 事件停在"等玩家点对话框"时，
`TurnStart / RunForces / TurnEnd / IncreaseDate` 会一路跑完，
AI 势力在后台把整个回合推进完，玩家点完对话框回来世界已经变了。

已在 `Scenario.Run()` 里与 `RenderEvent` 并列加了一道 `ScenarioEventManager.IsPlayingNow` 判断。

## 6. 怎么观测

### 6.1 必须先打开日志开关（否则全是盲测）

`Framework/Log/Log.cs`：

```csharp
[Conditional("SANGO_DEBUG")]
public static void Info(object message)
```

`Log.Info` 与 `Log.Warning` **都标了 `[Conditional("SANGO_DEBUG")]`** ——
未定义该宏时，编译器把调用**连同实参求值一起删掉**。
所以**看不到任何事件系统日志，不代表它没跑**；只有 `Log.Error` 一定会输出。

**操作**：Player Settings → Other Settings → Scripting Define Symbols 加上 `SANGO_DEBUG`。

### 6.2 打开后要搜的关键字

| 关键字 | 含义 |
| --- | --- |
| `剧本事件库：` | 加载报告（几个事件 / 几个文件失败） |
| `剧本事件系统初始化完成` | `Init()` 跑过了（订阅 + 条件/效果注册 + 加载都成功） |
| `剧本事件系统：开局年份` | `ScenarioStart` 到了，开局年份被捕获 |
| `事件开始播放：` | 闸门全过，交给了 `EventRunner` |
| `事件结束：` | 正常 / 中止（中止不计触发次数） |
| `登记定时事件：` / `定时事件到达触发点` | 跨回合链条 |
| `槽位 … 解析失败` | 槽位绑定失败（最常见的不触发原因） |
| `条件未满足：` | 条件树哪一条没过 |
| `本回合求值预算已用尽` / `本回合事件密度已达上限` | 性能/密度闸门挡下了 |
| `剧本事件系统：已启用` / `已关闭` | 总开关状态**发生变化**（不是每帧刷） |
| `让路给正在进行的演出，已暂缓` | 被旧体系 / 对话框挡住，已记入暂缓队列，下回合重试 |
| `暂缓队列已满` | 旧演出长时间不结束，本次触发被丢弃 |
| `JobTypes 含无法识别的任务名` | JSON 里写了不存在的 `MissionType` 名（例如 `Searching`） |
| `JobTypes 没有任何一项能识别` | 同上，已按"不过滤"处理 |

### 6.3 常见失败现象对照

| 现象 | 最可能的原因 |
| --- | --- |
| 完全没有任何日志 | `SANGO_DEBUG` 没开 |
| 有加载报告但从不播 | 触发时机不对（比如在等 `JobFinished` 却没做探索）；或 `MatchScope` 没过 |
| 播到一半卡住 | 某条指令在等外部（对话未关 / 单挑没结束） |
| 开局不弹桃园结义 | 三人有一个不是 `Alive`；或 `ScenarioFilter` 年份过滤 |
| 三顾茅庐只播一次 | 只做了一次"探索人才"；本事件每次探索只推进一顾 |
| 退出 Play 模式报 `UIRoot is being destroyed` | §5.1，已修；若复现说明还有第二条积压路径 |
| **探索做完了，2002 和 2003 都不播** | 正常：两者都按结果码过滤（`[-1]` 与 `[0]`）。若结果是"发现资金"（`>0`），两者都不关心 |
| **事件比预期晚一回合才播** | 正常：让路闸门生效了。上一回合有演出占着对话框时会被暂缓到本回合 |
| 事件播到一半，AI 势力不再推进 | 正常：`Scenario.Run()` 的 `IsPlayingNow` 判断在起作用 |

而早期代码**压根没有实现这个字段** —— 于是它被静默忽略、事件照常触发，
没人发现过滤其实从未生效（这也解释了为什么它一直"看起来能工作"）。

现在 `MatchJobFilter` 改为**容错**：枚举名无法识别时按"不过滤"处理并写告警，
避免一个笔误就让事件永久静默且毫无线索。要精确判定探索成败，**必须用 `JobSettled` + `JobResults`**。

### 7.5 ✅ 已修：`ScenarioYearCheck` 读错了年份来源

`ScenarioYearCheck` 的注释写着"剧本**起始**年份过滤……与 TimeRangeCheck 的区别：那是
'游戏进行到哪一年'，这里是'剧本从哪一年开局'"，但实现是：

```csharp
int startYear = Scenario.Cur.Info.year;   // ← 这是**当前**年份
```

而 `IncreaseDate()` 会 `Info.year += 1` —— 所以它与 `TimeRangeCheck` 的年判定**完全等价**，
配置者以为写的是"只在我这个剧本里生效"，实际上游戏推进到某个年份后它会**突然开始 / 停止生效**。

已改为读调度器在剧本开始时捕获的 `ScenarioEventManager.ScenarioStartYear`。
取不到开局年份时**不做过滤**（宁可多触发，也不要因数据缺失而静默失效）。
这与闸门⑤ `EventDatabase.MatchScenarioFilter` 用的是同一个来源，两者语义终于对齐了。

### 7.6 ✅ 已实现：`Trigger.DelayTurns` 原本是空声明

`EventTriggerDef.DelayTurns` 的注释写着"条件满足后延迟 N 回合再播放（用于事件的余波）"，
但 `TryFireEvent` 里**从来没有读过它** —— 又一个"写了不生效且毫无线索"的陷阱。

已补为闸门第 ⑩ 步：**前置条件全部满足之后**才登记，因为 `DelayTurns` 的语义是
"条件满足了，但先憋 N 回合再演"。实现上**复用定时队列**而不是自己记倒计时 ——
那样它天然随存档持久化、跨读档不丢，也不必再写一套推进逻辑。

两个必须处理的细节：

1. **防重复登记**。条件持续满足时每回合都会走到这一步，所以用**负数 `SourceEventId`**
   做标记（与事件里 `Op: Schedule` 的正数区分），已有待办就不再登记。
2. **不能把事件条件树当"取消条件"**。取消条件的求值路径
   `EventConditionEvaluator.IsCancelConditionMet` **不会设置 `database.fireCount` / `eventId`**，
   于是 `FireCountCompare` / `VarCompare` 这类依赖事件上下文的条件会算错
   （fireCount 取默认 1、eventId 取 0）。
   改为传 `null`，由 `FireScheduled` 走**正常求值路径**（它会把两个字段都设好）复核一遍 ——
   反而更准确。

> 顺带记录：`CancelIf` 的求值路径缺少 `fireCount` / `eventId` 是个**遗留限制**。
> 在 `Op: Schedule` 的 `CancelIf` 里写简单条件（`ForceAlive` 之类）没问题，
> 但**不要**写 `FireCountCompare` / `VarCompare`。

### 7.7 剩余待办

- **`JobSettled` 目前只覆盖"探索人才"**。`OnCityJobSearchingSettled` 只在
  `CityPersonSearchingEvent` 里抛；其它工作（内政、开发、登用）要同类能力，需各自补 hook。
- **让路时暂缓的实体可能已失效**（暂缓期间武将可能死亡 / 部队解散）。当前靠槽位解析失败自然兜底，
  没有显式判活 —— 若日志里频繁出现"槽位解析失败"，说明该补一层显式清理。
- **`JobResults` 与 `JobTypes` 同时配置时**，两者都必须通过（AND 语义）。目前没有场景用到，属未验证路径。
- **`CancelIf` 求值路径缺 `fireCount` / `eventId`**（见 §7.6 末尾）。
- §6.1 的 `SANGO_DEBUG` 开关仍需在 Player Settings 里手动打开。
