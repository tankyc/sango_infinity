# 部队决策逻辑审视报告

> 本轮共发现 **8 处问题**，**已全部修复**（编译 0 错误 0 警告）。

## 一、决策链总览

```
Troop.OnForceTurnStart()          每回合开始：重置 AIFinished / AIPrepared / isMissionPrepared
        ↓
Troop.DoAI(scenario)
        ├─ AIPrepare(scenario)    ★ 决策中枢（每回合仅一次）
        │     ├─ 被攻击 → 逃离            【需求3】
        │     ├─ 状态差 + 有补给队 → 求援   【需求4】
        │     └─ 断粮 / 兵少 / 士气低 → 就近返城
        │
        ├─ TroopMissionBehaviour  getter
        │     ├─ missionType == 0 且非玩家 → 自动 SetMission(TroopReturnCity, mBelongCity)  ← 关键副作用
        │     └─ Create(missionType) → 对应行为类
        │
        └─ temp.DoAI()           具体任务行为（进攻 / 防守 / 求援 / 补给 / 返城 …）
```

**城市侧联动**：`city.TroopMissionType` 驱动 `CityAI.Dispatch*Troop()` 持续派兵，
派兵上限依赖 `city.AttackTroopsCount`（= `allAttackTroops.Count`）。

## 二、你问的问题：部队求援后还会继续进攻吗？

### 结论：**不会，而且原任务会永久丢失**（已修复）

**原始链路**：

1. `AIPrepare` 触发求援 → `SetMission(TroopAskSupply, supplier.Id)`
2. `TroopAskSupply` 补满后 → `troop.ClearMission()` → `missionType = 0`
3. 下回合 `AIPrepare`：求援条件已不满足 → 跳过；撤退条件也不满足 → 直接 return
4. `missionType` 仍为 `0` → `TroopMissionBehaviour` getter 命中：
   ```csharp
   if (missionType == 0 && mBelongCity != null && !IsPlayerControl)
       SetMission(MissionType.TroopReturnCity, mBelongCity.Id);
   ```
5. 部队掉头返回**归属城**，`EnterCity` 后**解散部队**

**两个后果**：
- **原进攻任务（`TroopOccupyCity`）丢失**，部队再也不会回到前线
- 城市侧 `city.TroopMissionType` 仍是 `TroopOccupyCity`（不同步），会继续派**新**部队，
  但老部队白白损耗在往返路上

### 修复

`AIPrepare` 切换求援前**记录原任务**：

```csharp
missionParams1 = (int)missionType;   // 原任务类型
missionParams2 = missionTarget;      // 原任务目标
SetMission(MissionType.TroopAskSupply, supplier.Id);
```

求援收尾时**恢复**（`TroopAskSupply.FinishAskSupply`）：

```csharp
int prevType = troop.missionParams1;
int prevTarget = troop.missionParams2;
troop.ClearMission();                                  // 先取再清（ClearMission 会清零 params）
if (canRestore) troop.SetMission((MissionType)prevType, prevTarget);
```

新增配置 `askSupplyRestoreMission`（默认 `true`），可关闭以恢复旧行为。

## 三、其余 7 处问题

### 🔴 漏洞 2：求援完成条件过严 → 求援几乎永不结束

**问题**：`IsMissionComplete` 用 `!TroopSupplyTroop.NeedSupply(self)`，而
`CalcSupplyNeed` 只要 `troops < MaxTroops` 就返回正数（缺口 ≥ 100 即成立），
**部队只要没满编就永远"需要补给"** → 长期黏着补给队。

**修复**：改用 `TroopAskSupply.IsRecovered(t)` —— **兵力 ≥ 满编 30% 且粮草不告急**即视为恢复。

### ✅ 已移除：被攻击逃离（原漏洞 3）

**问题**：原条件仅 `IsBeAttackedThisTurn`（本回合被攻击过），
攻城时被守军**反击一次**（哪怕只掉 1 点兵）就有 **70%** 概率撤离 → 攻城几乎无法完成。

**处置**：先后收紧为"真的被打疼了"门槛（受伤 ≥ 20% 或兵力 < 50%），
后续按需求**完全移除该逻辑**。

现已清理的内容：
- `Troop.AIPrepare` 中被攻击逃离分支
- `Troop` 的 `beAttacked` / `lastAttackedTurn` / `beAttackedDamage` 字段、`MarkBeAttacked()`、`IsBeAttackedThisTurn`
- `ChangeTroops` 中的 `MarkBeAttacked(-num)` 调用
- `AIConfig` 的 `beAttackedRetreatDamagePercent` / `beAttackedRetreatHealthPercent` / `beAttackedRetreatChance`

**当前行为**：部队被攻击**不再触发主动撤离**，仅在"状态不佳（兵力 < 30% 或有断粮风险）+ 附近有补给队"时求援，
或在断粮 / 兵力过低 / 士气崩溃时返城（见《部队自行撤退条件清单》）。

### 🔴 漏洞 4：`AttackTroopsCount` 语义失真 → 前线兵力不足

**问题**：`AttackTroopsCount = allAttackTroops.Count`，统计的是**所有在外的战斗部队**，
**不区分任务**。去求援 / 撤离中的部队仍占名额 →
`DispatchOccupyTroop` 误判"已派够"而**不再补派**。

**修复**：`City` 新增只统计进攻任务的属性，`DispatchOccupyTroop` 改用它：

```csharp
public int AttackingTroopsCount   // 仅统计 missionType == TroopOccupyCity 且存活
if (city.AttackingTroopsCount >= maxAttackTroops) return;
```

### 🟡 漏洞 5：随机撤退逻辑重复且互相干扰

**问题**：`TroopOccupyCity.Prepare` 与 `TroopProtectCity.Prepare` 各自带有
`IsWithOutFood() == 1 && GameRandom.Chance(30)` 的随机撤退，与 `AIPrepare` 的统一撤退逻辑重复。

**修复**：两处删除，统一由 `AIPrepare` 处理（其 `outOfFood` 分支已覆盖）。

### 🟡 漏洞 6：`TroopMissionBehaviour.Create` 缺 `TroopStay` 分支

**问题**：`TroopStay` 类存在，但 `Create` 的 `switch` 无对应 `case` →
落入 `default` 返回 `TroopReturnCity`，`TroopStay` 实为死代码。

**修复**：补 `case (int)MissionType.TroopStay: return new TroopStay();`

### 🟡 漏洞 7：`TroopReturnCity` 的"发呆"分支

**问题**：当 `missionTarget` 指向**其它友城**（≠ `mBelongCity`）时：
`IsMissionComplete` 为真 → 目标非敌方 → `SetMission(TroopStay, 0)` + `Sango.Log.Error("发呆!!")`。
部队陷入无意义状态并刷错误日志。

**修复**：改为纠正目标回归属城。

```csharp
else if (troop.mBelongCity != null)
    Troop.SetMission(MissionType.TroopReturnCity, troop.mBelongCity.Id);
```

### ✅ 已修复 8：`Prepare` 中改任务导致行为对象与任务不一致

**问题**：`Troop.DoAI` 的流程是

```csharp
TroopMissionBehaviour temp = TroopMissionBehaviour;   // 此处可能已被 getter 改过 missionType
if (!isMissionPrepared) { temp.Prepare(this, scenario); }  // Prepare 内部可能再次 SetMission
...
if (!temp.DoAI(this, scenario)) return false;          // 但 temp 仍是旧行为对象！
```

`TroopOccupyCity.Prepare` / `TroopProtectCity.Prepare` / `TroopReturnCity.Prepare`
**都会在 `Prepare` 中 `SetMission`**，导致随后执行的 `temp.DoAI` 用的是**旧行为对象 + 新任务状态**，
`TargetCity` / `priorityActionData` 与新任务不匹配，表现为**本回合空转**。

**修复**：在 `temp.Prepare` 之后**循环重新读取** `TroopMissionBehaviour`，
直到行为对象与任务一致（切换可能链式发生：进攻 → 协防 → 返城）：

```csharp
for (int guard = 0; guard < 4; guard++)          // 上限 4 次防死循环
{
    TroopMissionBehaviour refreshed = TroopMissionBehaviour;
    if (refreshed == null) { /* 无任务：结束本回合 */ return true; }

    if (refreshed == temp) break;                // 已一致，跳出

    temp = refreshed;
    if (!isMissionPrepared)                      // 新对象若未准备过则补一次
    {
        temp.Prepare(this, scenario);
        isMissionPrepared = true;
    }
}
```

**效果**：任务在 `Prepare` 中被切换后，**本回合即按新任务行动**（例如进攻部队在目标失效的当回合就转为返城 / 协防），
不再浪费一个回合。

## 四、其它可优化点（未修改）

| 项 | 说明 |
|---|---|
| `TroopHarassCity` 无行为类 | `MissionType` 有定义但目录中无 `TroopHarassCity.cs`，落入 `default` |
| `city.TroopMissionType` 与部队任务不同步 | 部队因求援 / 撤离脱离战线时，城市侧仍认为在进攻。若希望城市感知，可在 `AttackTroopsCount` 之外再暴露"进攻受阻"信号 |
| `TroopAskSupply` 搜索范围 12 格偏大 | 残兵可能跨半张地图找补给队。可调小 `askSupplySearchRange` |
| 撤离无"回归"机制 | 被攻击撤离到城市即 `EnterCity` 解散，兵员回城。若希望"伤愈后再出阵"，需城市侧重新派兵（当前已由 `Dispatch*Troop` 覆盖） |
