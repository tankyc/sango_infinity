### C1. JSON 库：`TKNewtonsoft.Json` → `Newtonsoft.Json`（**全局**）

**影响范围**：`事件系统设计.md` §8.2 的全部代码契约、所有 JSON 相关示例代码。

```csharp
// ❌ 旧（已失效）
using TKNewtonsoft.Json;
using TKNewtonsoft.Json.Linq;

// ✅ 新
using Newtonsoft.Json;
using Newtonsoft.Json.Linq;
```

**注意**：`[JsonObject(MemberSerialization.OptIn)]` / `[JsonProperty]` / `[JsonConverter(typeof(X))]` / `[JsonExtensionData]` 这些特性原版都有，**语义不变**，无需改动。`JsonConverter<T>` 的抽象签名与原版一致（见 `ItemStoreConverter.cs`）。仍有 5 个文件残留 `using TKNewtonsoft`，实施时先确认它们是否兼容。

### C2. Person 五维数组化（**影响条件/效果实现**）

```csharp
// Person.cs:268
[JsonProperty][JsonConverter(typeof(PersonAttributeValueConverter))]
public PersonAttributeValue command = new PersonAttributeValue();
```

**影响**：
- 事件条件 `PersonAttributeCheck` / `PersonAttributeCompare` **不能把五维当 `int` 直接读**，必须走项目规则第 23 条规定的公共属性（`Command` / `Strength` / `Intelligence` / `Politics` / `Glamour`）。
- **不要**在事件 JSON 里序列化 `Person` 对象本身（结构已变为数组），只存 **Id**。这与既有设计一致，无需改。
- `参数值` 读取要经过 `PersonAttributeValue.Value`（含装备加成）。

### C3. 结义判定必须用 `IsBrotherGroupmate`（**不是 `IsBrother`**）

### C5. 舌战无法演出（**新发现的限制**）

```csharp
// DebateChallengeFlow.cs:48
ForceNoView = true;   // 界面未完成，恒后台结算
```

**影响**：
- `Op: Debate` **目前不能做舌战演出**，只能后台结算 + 用 `DebateConsequence` 回写结果。
- "诸葛亮舌战群儒"、"骂死王朗" → 一期只能用 **`Talk` 台词链模拟**，等舌战界面完成后才能接真实舌战。
- 反过来说，`DebateConsequence`（订阅 `OnDebateEnd`，挑战方胜则**把发起行为改判为成功**）是一个很有用的现成机制，事件触发的登用/外交可以用它做"翻盘"。

**设计调整**：`Op: Debate` 拆成两个指令
- `Debate`（真实舌战，等界面完成）
- `DebateFake`（一期方案：台词链 + 直接结算，无舌战 UI）

### C6. 必须接入 `ScenarioLifecycle` 的生命周期（**关键**）

`Game/System/ScenarioLifecycle.cs` 是一份**显式收尾清单**，读档与回主菜单都走它：

```
1) RenderEvent.Instance.Reset()
2) GameSystemManager.Instance.Done()        ← 触发所有 GameSystem 的 OnDestroy
3) GameDialog.Instance.Reset()
4) PlayerMessage.ClearMessages()
5) GameController.Instance.ResetInputState()
6) Scenario.Cur.OnGameShutdown()
7) AIConfig.Reset()
8) Player.currentTurnCount = 0
9) GameEventBaseline.Restore()              ← 把 GameEvent 静态订阅整体还原回"开局前"
9.5) DeploymentShadow.Clear() + DeploymentState.Clear()
10) GameEventDiagnostics.Snapshot("shutdown-end")
```

**事件系统必须做的三件事**：

1. **`ScenarioEventManager` 做成 `GameSystem`** → 第 2 步 `GameSystemManager.Done()` 会自动触发它的 `OnDestroy`，在其中清 `ScheduledEvents` / `EventRunState` / 结束 `EventRunner`。
2. **在清单里显式加一步**（建议第 6.5 步，紧跟剧本收尾）：
   ```csharp
   // 6.5) 事件系统运行期状态（定时队列 / 触发计数 / 旗标 / 私有变量）
   ScenarioEventManager.Instance.Clear();
   ```
   理由：`Scenario.OnGameShutdown()` 只清剧本自身的数据集合，事件系统的**静态/单例状态**不在其覆盖范围。
3. **明确订阅策略**：`GameEventBaseline.Restore()` 会把每个委托**整体替换回基线**（基线里有 `Game.Init` 订的应用级订阅）。
   - **方案 A（推荐）**：事件系统在 **`Game.Init` 时订阅一次**（应用级）→ 基线保住，读档不会被清掉，`Clear()` 只清数据。
   - **方案 B**：每次开局重订 → 基线会正确清掉残留，但必须保证"开局必订"。
   - **`EventRunner` 是每剧本创建的**，不入基线，必须自身对称退订。

### C7. `MissionType` 新枚举必须追加在末尾

`4fe4002c` 明确：`PlayerTroop*` 追加在 `MissionType` **末尾**，以兼容存档里的 `int`。

**影响**：若事件系统要新增 `MissionType`（如"事件锁定"任务），**必须追加在末尾**，不得插入中间。

### N3. 人才部署系统与事件的效果冲突（**新风险**）

`DeploymentExecutor` 会**自动在势力内调动空闲武将**。若事件刚把某武将放到指定城，而该武将 `IsFree == true`，部署系统下一回合可能把他调走。

**冲突面评估**：
- ✅ **不受影响**：在野武将（`BelongForce == null`）—— 部署系统只处理有势力的人。"三顾茅庐"的诸葛亮在野，安全。
- ⚠ **受影响**：事件把某武将"放到某城并要求他待命"（如"关羽守荆州"）
- ✅ **天然免疫**：若事件给该武将 `SetMission(...)`，`CanTransfer` 里 `if (!person.IsFree) return Deny("在途 / 部队中 / 有任务")` 会跳过

**处理方案**：
- **方案 A（推荐）**：事件需要"锁定位置"时，给武将设一个 `MissionType` 使 `IsFree == false`（注意 C7：新枚举必须追加末尾）
- **方案 B**：`EventRunState` 记录"事件锁定武将"，在 `OnForceAIPrepare` / `OnCityAIPrepare` 时临时禁用其调动
- 一期可先不处理，在事件设计规范里写明"需要待命的武将必须用 `SetMission` 占住"

### N4. 双 AI 任务体系（事件下达任务时要注意选对体系）

`4fe4002c` 后，玩家部队与 AI 部队走**两套物理分离的 MissionType / 行为类**：

| 体系 | 枚举 | 行为类 |
| --- | --- | --- |
| AI | `MissionType.TroopMovetoCity` 等 | `TroopMissionBehaviour` 默认分支 |
| 玩家委任 | `MissionType.PlayerTroopMovetoCity` 等 | `PlayerTroopMissions` |

`Troop.SetMission` 内部会把"玩家第一军团"自动映射为 `PlayerTroop*`。

**影响**：事件给玩家势力的部队下达任务时，要意识到这条自动映射；给 AI 势力下达时走默认分支。

### N5. `GameEventDiagnostics` 可复用为事件调试的参考

`GameEventDiagnostics.Snapshot(tag)` / `Capture` / `Diff` 是"反射遍历静态委托并快照"的现成工具，事件调试面板（D21）可参考其实现风格，但**事件调试需要的是"条件求值明细"而非"订阅数"**，仍需自建。
