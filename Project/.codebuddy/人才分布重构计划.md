# AI 人才部署系统 —— 架构设计（2026-09-24 定稿）

> **本文档替换此前所有版本**（旧方案"保留 `PersonHole` + 抽离 ring 填充逻辑 + 逐阶改造"已作废）。
> **需求约束（第 1-7 条决策）保留**，见 §0；被抛弃的是**架构**：数据结构、调用链、职责划分、扩展方式。
> 原则：**不在旧骨架上打补丁**，重新设计一套能承载"圈层 / 威胁 / 发展 / 运输 / 港关 / 分层"的模型。

## 0. 需求约束（不变）

| # | 约束 |
|---|---|
| 1 | 部署 = **改户口**：走 `Person.TransformToCity`（户口立即变更、武将自行走行程，非瞬移） |
| 2 | 席位基数：小 3 / 中 4 / 大 5 / 巨 6；单城不超势力总人数 40% |
| 3 | 港关：按是否边境 + 威胁动态，**最低 0 人、常驻可达 2 人**；质量优先军事（守备） |
| 4 | 生效范围：AI 势力始终；玩家势力仅"**非第一军团** + 人才开关打开" |
| 5 | **允许跨圈层交换**；圈层权重随威胁调整；需要**调整间隔/防抖**机制 |
| 6 | 接受 AI 变强 |
| 7 | **纳入运输势态**（源城/目标/开关/港关中转/线路安全） |

## 1. 被抛弃的旧架构（不再修补）

| 旧结构 | 位置 | 为什么必须丢 |
|---|---|---|
| `City.PersonHole` 标量需求 | `City.cs:401` | 只能表达"缺几人"，无法表达"缺什么样的人"；还被当计数器 `--`（`ForceAI.cs:2230`）污染 |
| `Force.PrepareCityPersonHole` 均分公式 | `Force.cs:1466-1524` | 份额算法病态（`avg/BorderCityCount` 无上限、`upSeat=boderSeat-15` 让次前线失效），实测退化为"每城补 3 人" |
| 环形填充调人循环 | `ForceAI.cs:2214-2249` | "按圈层硬填"无法表达威胁/发展/运输；就地排序污染 `freePersons` |
| 三处各自调人 | `ForceAI.cs:2139`、`CorpsAI.cs:22`、`CityAI.cs:590/727/761` | 同一动作三份实现、策略分歧、港关被抽空 |
| 每回合全量重算 | `Force.OnForceTurnStart` | 无谓重算 → 横跳；只能靠魔数冷却压制 |
| 硬编码阈值 | `MilitaryAbilityMax=350`（`ForceAI.cs:2145`） | 不可配、不可观测 |

**结论**：旧结构的问题不是"实现得不好"，而是**模型层级错了** —— 它用"人数"表达"用人"，因此永远无法变聪明。

## 2. 新架构总览

```
┌──────────────────────────────────────────────────────────────────────┐
│ ① 编制层 CityEstablishment                                            │
│    城况画像 → 岗位表（Post[]）                                         │
│    岗位 = 类型(军事/开发/后勤/运输/守备) + 优先级 + 硬软 + 能力权重向量   │
├──────────────────────────────────────────────────────────────────────┤
│ ② 求解层 DeploymentSolver                                             │
│    岗位 × 人选 → 匹配分 → 贪心指派 + 局部改进 → DeploymentPlan          │
│    （含：未满足岗位清单 + 原因链）                                       │
├──────────────────────────────────────────────────────────────────────┤
│ ③ 执行层 DeploymentExecutor（唯一允许调动的地方）                       │
│    合法性闸门（守备下限/被围/在途/主公军团长/开关）→ TransformToCity      │
│    写回 Assignment（在岗状态）→ 发事件 → 记原因日志                      │
├──────────────────────────────────────────────────────────────────────┤
│ ④ 稳态层 DeploymentState + 失效信号（Invalidation）                    │
│    只在"真正变化"时重算受影响范围；不使用冷却常量压制                     │
├──────────────────────────────────────────────────────────────────────┤
│ ⑤ 观测层：DeploymentPlan 原因链 → GameAIDebug 面板 / 日志 / 模拟器       │
└──────────────────────────────────────────────────────────────────────┘
```

**与旧架构的三个本质差别**

| 维度 | 旧 | 新 |
|---|---|---|
| 需求表达 | 一个整数（缺几人） | **岗位表**（缺什么样的人、什么优先级、硬性还是弹性） |
| 触发方式 | 每回合全量重算 | **失效信号驱动**，只算受影响范围 |
| 执行入口 | 三处各自调 `TransformToCity` | **唯一执行器 + 合法性闸门** |

## 3. 数据模型

```cs
// 岗位类型（扩展点：以后加"外交"、"计略"只需加枚举 + 规则）
public enum PostKind { Military, Develop, Logistics, Transport, Garrison }

public struct Post
{
    public PostKind kind;
    public int      priority;      // 同城内优先满足顺序（小=优先）
    public bool     required;      // true=硬性（无人则必须解释原因）
    public PostFit  weights;       // 能力权重向量：统率/武力/智力/政治/魅力 + 搬运特性
    public int      cityId;
    public int      assignedId;    // 在岗武将（0=空缺）
}

public struct PostFit          // 能力权重向量（可配置）
{
    public float command, strength, intelligence, politics, glamour, transport;
}

// 运行期状态（不序列化）
public struct Assignment
{
    public int  postKind;
    public int  cityId;
    public int  sinceTurn;         // 用于防抖与展示
}
```

**不引入任何新的存档字段**（`Assignment` 与岗位表均为运行期推导；旧 `City.PersonHole` 停用但字段保留，避免老存档键变化）。

## 4. 编制层：城况 → 岗位表

**输入画像（一次性采集，复用既有设施）**

| 画像项 | 来源 |
|---|---|
| 城等级 | `City.CityLevelType` |
| 圈层 | `City.borderLine` / `IsBorderCity`（`City.cs:356-360`） |
| 威胁 | `BattleSituation.EvaluateCityThreat(city)` → `threatLevel`（`BattleSituation.cs:640-664`） |
| 被围 | `CitySituation.isUnderSiege` |
| 发展缺口 | `1 - avg(commerce/CommerceLimit, agriculture/AgricultureLimit, tech/techLimit)`（`City.cs:211-219`） |
| 兵力/兵装缺口 | `troops/troopsLimit`、`itemStore` |
| 港关 | `IsPort()` / `IsGate()`（`BuildingBase.cs:139-146`）+ `BelongCity` |
| 运输势态 | 源城条件（`CityAI.cs:592-598`）、目标吃紧线（`:757-761`）、`TransportDisable`（`:600`） |
| 势力预算 | 总人数、城池数、个性（`ForceAI.AIPersonalityType`，`ForceAI.cs:15-22`） |

**岗位生成规则（声明式，可配）**

| 规则 | 生成岗位 |
|---|---|
| 任意城 | 军事 × levelSeat[城等级] 的**基础编制**（按城况再切分类型） |
| `borderLine == 0` | **军事** +1（`required = true`） |
| 威胁升档（中/高） | **军事** +1 / +2（高威胁 `required = true`） |
| 开发缺口大（分档） | **开发** +1 ~ +3（`required = false`，弹性可空） |
| 港关 | **守备** `clamp( (边境?1:0) + (高威胁?1:0), 0, 2 )`（≥1 时 `required = true`），权重偏统率/武力 |
| 运输源城且军团未禁运输 | **运输** +1（权重偏搬运特性 `HasFeatrue(8)`） |
| `borderLine >= 2` 且治安/粮草吃紧 | **后勤** +1（权重偏政治/魅力） |
| **被围城** | **不生成接收岗位**（负向规则），并标记"可撤离" |

**编制上限**：`Σ岗位 ≤ floor(势力总人数 × 40%)`（决策 2）；若总岗位 > 可用人力 → 按 `priority` 截断（**降级顺序显式化**，见 §6）。

## 5. 求解层：岗位 × 人选

**匹配分**

```
fit(p, post) = post.weights · normalize(p)      // 向量点积（统率/武力/智力/政治/魅力/搬运）
travel(post.city, p) = DistanceDays(post.city, p.CurrentCity) / turnDays(10) × costPerTurn
score = fit − travel − (跨圈层 ? crossRingCost : 0)
```

**指派算法**

1. 岗位按 `priority` 分档；同档内按 `required` 优先
2. 对每个岗位取 `score` 最高的**空闲**人选（贪心）
3. 一轮结束后做**局部改进**：尝试两两交换（同档岗位间）若能提升总分则交换（规模小，1-2 轮足够）
4. 剩余岗位进入"未满足清单"，附原因（无人/被闸门否决/超预算）

> 复杂度：`O(P·C)` 级别（P 岗位数、C 候选人数，通常几百），事件驱动触发，非每帧/非每回合。

## 6. 稳态层：失效驱动 + 防抖（取代冷却常量）

**失效信号（任一触发即重算受影响范围）**

| 信号 | 影响范围 |
|---|---|
| 城况画像跨档（等级/圈层/威胁档/开发缺口档/运输势态翻转） | 该城岗位表 + 相关候选人 |
| 城池得失 / 被围 / 解围 | 该城 ± 邻接圈层 |
| 武将变动（加入/被俘/死亡/在途到达） | 全局预算（人数变化） |
| 势力人数剧烈变化 | 全局 |

**防抖**：同一武将 `debounceTurns`（默认 2）回合内不再被调动；同一城每回合最多变动 1 人（可配）。
**降级顺序**（编制 > 人力时牺牲谁）：`被围城接收岗 → 弹性开发岗 → 后勤岗 → 非边境港关守备 → 后方军事岗`，前线军事岗最后动（硬性）。

## 7. 执行层：唯一执行器 + 合法性闸门

```cs
DeploymentExecutor.CanTransfer(person, dest, postKind) → (bool, reason)
  闸门：
    · 归属合法性：BelongForce/BelongCorps 允许（跨军团是否需授权 → 可配）
    · 特殊身份：主公 / 军团长 / 太守 → 按现有 OnWillChangeToCity 语义处理
    · 状态：在途 / 被俘 / 死亡 / 已在目标城 → 拒绝
    · 目标城：被围 → 拒绝入内（决策 3 的负向规则）
    · 源城：港关/前线是否跌破**守备下限** → 拒绝
    · 开关：玩家势力人才开关、TransportDisable
    · 编制：目标城对应岗位空缺存在（不允许超编）
DeploymentExecutor.Transfer(person, post)
  → 这是 AI 部署范畴内【唯一】调用 Person.TransformToCity 的地方
  → 写 Assignment、发 GameEvent（供 UI 显示任命）、记原因日志
```

现状需要一并收口的调用点：`ForceAI.cs:2228`、`CorpsAI.cs:77/102`、`CityAI.cs:590/727`、**`CityAI.cs:761-770`（港关被抽空的元凶）**。外交/俘虏等非部署路径保持原样。

## 10. 可观测性（一等公民）

`DeploymentPlan` 每条记录带**原因链**，例如：

```
[许昌] 岗位 军事#2(required) ← 张辽  原因: 圈层0 + 高威胁(2400) | 匹配0.82 行程0.1
[宛城] 岗位 开发#1(soft)   ← 荀彧  原因: 开发缺口62% | 匹配0.91 行程0.2
[港口] 岗位 守备#1(required) ← 空缺 原因: 候选池无人满足 统率≥70 且 非在途
```

直接喂给既有 `GameAIDebug` 面板；也是验收"是否更依赖形势"的唯一客观依据。

## A8. 成本项与总分

```
总分 = 能力适配 − 行程成本 − 跨圈层成本
行程成本   = DistanceDays(目标城) / 10 × costPerTurn(1.0)   → 1天=0.10 10天=1.00 30天=3.00
跨圈层成本 = crossRingCost(1.5)（户口城 borderLine 与目标城不同即计）
```

**由数值表暴露出的三个调参点**（建议，等你定）：

| # | 现象 | 建议 |
|---|---|---|
| 1 | `costPerTurn = 1.0` 偏大：猛将 vs 谋臣的军事差仅 **0.46 分** ≈ 5 天行程 → 稍远就"成本主导" | 降到 **0.3–0.5** |
| 2 | `crossRingCost = 1.5` ≈ 15 天行程，实际会**强烈抑制**跨层交换，与决策 5「允许跨层」相悖 | 降到 **0.6–1.0** |
| 3 | 编制总量偏大：12 城 / 60 人的示例势力合计 **82 个岗位**（> 总人数），会长期存在硬性空缺 | `levelSeat` 降一档（如 `[2,3,4,5]`）或降低圈层/威胁加成 |

> 另：表 A 可见"前线城在开发缺口大时仍拿开发岗"（如缺口 100% 时 军5 开3）。若要战时抑制内政，加一条"威胁 ≥ 高档 / 被围时开发岗降权"规则即可。

# 附录 D：军事编制用"预想兵力"（抗抖动）

**改动来源（需求）**：兵力情况要做**预想值**而非当前值，否则会被 出征 / 灾害 / 被攻击 等影响。

## D1. 预想兵力的构成

```
预想兵力 = max( 兵力上限 × troopExpectFill(0.8) , 长期观察值 EMA )
          再与"当前兵力"取大（useCurrentTroopsWhenHigher，只上不下）
          最后裁剪到 [0, 兵力上限]
长期观察值 EMA = 每回合 old + (当前兵力 − old) × troopObserveAlpha(0.25)
```

三段的用意：

| 来源 | 作用 |
|---|---|
| **容量部分**（上限 × 0.8） | 编制基本盘：由城池规模决定，**不受瞬时事件影响** |
| **观察部分**（慢速 EMA） | 长期修正：城池若长期缺兵，编制会缓慢下调 |
| **只上不下** | 囤兵准备出征能被承认；但出征/受灾导致骤降时**不会立刻缩编** |

**运行期状态**放在 `Game/Object/Deploy/DeploymentState.cs`（**不序列化、不进存档**），
由 `ScenarioLifecycle` 第 9.5 步 `Clear()` 复位。Phase B 的"在岗指派"也会放这里。

## D2. 新增参数（`AIConfig.json` → `deployment`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `troopExpectFill` | 0.8 | 预想兵力的容量比：`兵力上限 × 该值` |
| `troopObserveAlpha` | 0.25 | 兵力观察值的每回合 EMA 系数 |
| `useCurrentTroopsWhenHigher` | true | 当前兵力高于预想时采用当前值（只上不下） |

## D3. 实测：12 回合兵力曲线（后方 Lv4，上限 20000，每将 10000）

| 回合 | 兵力 | 情形 | 预想兵力 | 军事（旧=当前 / 新=预想） | 征兵 |
|---|---|---|---|---|---|
| 1–3 | 20000 | 囤兵 | 20000 | 旧 2 / **新 2** | 0 |
| 4 | 6000 | 出征归来 | 16500 | 旧 1 / **新 2** | 2 |
| 5–7 | 0 | 被打残 | 16000 | 旧 **0** / **新 2** | 2 |
| 8–12 | 20000 | 再囤兵 | 20000 | 旧 2 / **新 2** | 0 |

**⇒ 军事编制变动次数：新式 0 次 / 旧式 3 次** ✓（这正是"将军被反复调动"的根因）

小城（上限 4000，后方，兵 0）：预想 = 3200 → 军事 1、征兵 2、开发 0 ✓

## D4. 职责划分（重要）

| 岗位 | 依据 | 理由 |
|---|---|---|
| **军事** | **预想兵力** | 将军的驻地要稳定，不能因一次出征就缩编 |
| **征兵** | **当前兵力**（`兵力/上限`） | 它的职责就是应急补兵，必须反映真实缺口 |
| **运输** | 当前兵力/粮草 | 是否"富余到能外运"是实时判断 |

报告依据文本会同时给出两者，便于核对：
`军事: 常规 预想兵力16000(当前0/上限20000)`

## D5. 验证记录

| # | 断言 | 结果 |
|---|---|---|
| 1 | 新参数与 `DeploymentState.Observe/GetExpectedTroops/Clear` 就位 | ✓ |
| 2 | 出征/被打残期间军事编制保持 2 不缩编 | ✓ 表 D3 |
| 3 | 同一曲线下"旧式（当前兵力）"会跳 3 次 | ✓ 对照 |
| 4 | 征兵岗在真缺兵时照常出现（不抗抖动） | ✓ |
| 5 | 小城按容量给出合理编制（预想 3200 → 军事 1） | ✓ |
| 6 | 运行期状态不序列化、收尾复位 | ✓ |

**待调参点**：容量下限意味着"长期空城仍按容量留军事岗"。若希望空城也缩编，
把 `troopExpectFill` 调低（例如 0.4）或把 `useCurrentTroopsWhenHigher` 关掉即可。

# 附录 E：预想兵力按经济状况修正

**改动来源（需求）**：预想兵力可以根据经济状况修正。

## E1. 公式

```
经济系数 = clamp(troopEcoBase(0.5) + 0.3×粮草填充率 + 0.2×金钱填充率, troopEcoFloor(0.4), 1.0)
预想兵力 = 兵力上限 × troopExpectFill(0.8) × 经济系数        ← 容量部分
          再与 兵力长期 EMA 取大 → 再与当前兵力取大（只上不下）→ 裁剪到 [0, 上限]
经济系数同样做慢速 EMA（troopEcoAlpha 0.25）—— 灾害/围城不会立刻缩编
```

来源：`CitySituation.foodFill` / `goldFill`（`CitySituation.cs:188-190`）。

## E2. 新增参数（`AIConfig.json` → `deployment`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `troopEcoAdjust` | true | 是否按经济修正预想兵力 |
| `troopEcoBase` | 0.5 | 经济系数基数（粮钱全空时的下限来源） |
| `troopEcoFoodWeight` | 0.3 | 粮草填充率权重 |
| `troopEcoGoldWeight` | 0.2 | 金钱填充率权重 |
| `troopEcoFloor` | 0.4 | 经济系数下限（再穷也保留的比例） |
| `troopEcoAlpha` | 0.25 | 经济系数慢速均值系数（抗抖动） |

## E3. 实测

**经济系数**：粮钱满 **1.00** ／ 半仓 **0.75** ／ 空仓 **0.50** ✓

**灾害曲线**（上限 20000、兵力 0、粮钱 8 回合由丰转灾再恢复）：

| 回合 | 粮钱 | 原始系数 | 平滑后预想兵力 | 军事 | 征兵 |
|---|---|---|---|---|---|
| 1–3 | 1.0 丰 | 1.00 | 16000 | 2 | 2 |
| 4 | 0.0 灾害 | 0.50 | 14000 | **2**（不立刻缩编） | 2 |
| 5–7 | 0.0 | 0.50 | 12500 → 11375 → 10532 | 2 | 2 |
| 8 | 0.0 | 0.50 | 9899 | **1**（灾后第 5 回合才缩编） | 2 |
| 9–12 | 1.0 恢复 | 1.00 | 11424 → … → 14070 | 2 | 2 |

**⇒ 12 回合军事编制只变动 2 次**（而非"灾害当天就跳"）✓

**只上不下**：城内实际有 20000 兵时，经济满 / 空都得到预想 20000 ✓（兵在就得有人带，经济只影响"该养多少兵"的容量预期）

# 附录 G：预想资源值（资金 / 粮草 / 兵装）+ 离边境距离的开发修正

**改动来源（需求）**：同时做出预想资金 / 预想粮草 / 预想兵装值，用于计算城池**基于离边境距离**的开发修正。

## G1. 预想资源值（与预想兵力同一套抗抖动口径）

```
预想资金 = max( 金库上限 × goldExpectFill(0.7) , 资金长期均值 EMA )
预想粮草 = max( 粮仓上限 × foodExpectFill(0.7) , 粮草长期均值 EMA )
预想兵装 = 兵装长期均值 EMA（首次观察时取当前兵装数）
资源观察 EMA = old + (当前值 − old) × resourceObserveAlpha(0.25)
```

要点：**运输搬走粮草、赏赐花掉金钱、一次性征兵消耗兵装，都不会让开发编制立刻变**。

## G2. 开发修正（离边境距离 × 资源富裕度）

```
离边境距离系数 = devRingFactor[borderLine]        // 圈层 = 离边境跳数
                  默认 [0]=0.5（边境） [1]=0.8（次前线） [2]=1.0（后方） [3+]=1.15（纵深）

资源富裕度 = ( 预想资金/金库上限 + 预想粮草/粮仓上限 + 预想兵装/预想兵力 ) / 3   （各项 0..1）

开发修正 = clamp( 距离系数 × ( devResourceBase(0.7) + 0.3 × 资源富裕度 ), devModMin(0.3), devModMax(1.5) )

开发岗位数 = round( (内政点数÷3 取整 + 缺口加派) × 开发修正 )，再受 devSeatMax 封顶
```

直观含义：**前线打对折**（资源优先军需、随时可能失守），**纵深富城最多加成到 1.5 倍**。

## G3. 新增参数（`AIConfig.json` → `deployment`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `goldExpectFill` / `foodExpectFill` | 0.7 / 0.7 | 预想资金的容量下限基线（同时是"富裕度下限"的来源，**想要资源影响更强就调低**） |
| `resourceObserveAlpha` | 0.25 | 资源观察值 EMA 系数 |
| `devRingFactor` | `[0.5, 0.8, 1.0, 1.15]` | 离边境距离系数（下标 = 圈层，超出取最后一项） |
| `devResourceBase` | 0.7 | 资源富裕度对修正的贡献下限 |
| `devModMin` / `devModMax` | 0.3 / 1.5 | 修正上下限 |

# 附录 H：武将 ↔ 岗位匹配 与 边境优先原则

**改动来源（需求）**：武将适合什么岗位（按能力），以及分配是否按**边境优先**原则。

## H1. 现状核查（改前）

| 需求 | 改前状态 |
|---|---|
| 武将按能力匹配岗位 | **已实现** —— 每类岗位有独立能力权重向量，人选按 `Score = 能力适配 − 行程成本 − 跨圈层成本` 挑（见附录 A7 / C1） |
| 边境优先 | **只体现在编制数量上**（前线岗位更多）；**分配顺序里军事岗按"威胁等级"排，不按圈层** ✗ |

## H2. 改后：分配顺序（"谁先拿到稀缺的人"）

`DeploymentSolver.CompareForAssign()`（`public static`，可直接复现验证）：

```
1) 硬性岗位优先（港关守备 / 前线·高威胁的第一军事岗）
2) 岗位优先级：守备0 → 军事1 → 征兵2 → 军备3 → 训练4 → 搜索5 → 运输6 → 开发7 → 后勤8
3) 分类决胜：
   · 军事 / 守备岗 → 【边境优先】圈层小的先拿人（0 = 边境），同圈层再比威胁高的优先
   · 内政岗       → 开发缺口大的先拿人，同缺口时更靠边境的先拿
4) 城 id / 岗位类型兜底（结果稳定可复现）
```

**与"编制数量"的分工**（两者互补）：

| 层面 | 依据 | 作用 |
|---|---|---|
| **编制数量**（附录 B/C） | 圈层 + 威胁 + 兵力 + 内政 + 资源 | 决定**每座城有几个什么岗位** |
| **分配顺序**（本节） | 硬性 → 优先级 → **边境优先 / 缺口优先** | 决定**人不够时先给谁** |
| **人选打分**（附录 A7） | 能力权重向量 − 行程 − 跨圈层 | 决定**具体派谁** |

## H3. 实测（复现排序，前 3 项为军事岗）

| 序 | 岗位 | 说明 |

# 附录 K：圈层 / 边境是怎么判定的（含两个风险）

## K1. 真实来源：`Force.UpdateTurnInfo`（`Force.cs:840-914`）

每个势力回合重算一遍本势力所在城的 `borderLine`：

```
① 己方每座 IsCity() 城：borderLine = -1（未定）
② 若某个相邻城「与本城不是同一势力」→ borderLine = 0  （0 = 边境）
③ 循环直到收敛（while hasNoCheckBorder）：
     对仍为 -1 的己方城：取「相邻城中 borderLine ≥ 0 的最小值 + 1」
```

- `City.borderLine`：`internal int`（`City.cs:352`）；`IsBorderCity => borderLine == 0`（`:356`）；`BorderLine` 只读公开（`:360`）
- **判定"边境" = 与不同势力接壤**（`neighbor.IsSameForce(c)` 为假）

## K2. 新系统用到它的 6 处

| # | 用途 | 代码 | 规则 |
|---|---|---|---|
| 1 | 军事基础编制切分 | `CityEstablishment.Build` | 前线 100% 军事 / 次前线 ≈60% / 后方 ≈40% |
| 2 | 圈层加成 | 同上 | 前线 +2、次前线 +1 |
| 3 | 开发修正 | `CalcDevelopRingFactor` | `devRingFactor[borderLine]` = 0.5 / 0.8 / 1.0 / 1.15 |
| 4 | **分配顺序（边境优先）** | `DeploymentSolver.CompareForAssign` | 军事岗：圈层小的先拿人 |
| 5 | 港关守备 | `CityEstablishment.Build` | `clamp((边境?1:0)+(高威胁?1:0), 0, 2)` |
| 6 | 跨圈层成本 / 后勤岗 | `Score` / `Build` | 跨层 +1.5；`borderLine >= 2` 才可能出后勤岗 |

## K3. ⚠️ 风险 R1：港关永远是"边境"

`UpdateTurnInfo` 里圈层计算被包在 `if (c.IsCity())` 内（`Force.cs:860`）→
**港口 / 关卡的 `borderLine` 永远是默认值 0 = 边境** → 于是：

- 规则 5 变成"所有港关至少 1 人"，**决策 3 说的"最低 0 人"在实战中不会出现**；
- 规则 1/2/3/4/6 对港关也会按"最前线"处理。

**建议改法**（1 处新方法 + 4 处调用）：港关以其**归属都市**的圈层为准：

```cs
/// 取"形势圈层"：港关/关卡的 borderLine 恒为 0（UpdateTurnInfo 只对 IsCity() 计算），
/// 因此港关按其归属都市（City.BelongCity）的圈层判断，否则所有港关都会被当成前线。
public static int ResolveRing(City city)
{
    if (city == null) return 0;
    if (city.IsPort() || city.IsGate())
    {
        City parent = city.BelongCity;
        if (parent != null && parent != city) return ResolveRing(parent);
    }
    return city.borderLine;
}
```

调用点：`CityEstablishment.Build`（`isBorder` / `ringSeat` / 后勤判断 / 开发系数）、
`DeploymentSolver`（`ringOfCity` 构建、`CityStamp`、报告标签）。

## K4. ⚠️ 风险 R2：`borderLine` 可能是 `-1`（未定）

收敛标志写在循环内部（`Force.cs:907`：`hasNoCheckBorder = c.borderLine == -1;` 覆盖式赋值）→
**与遍历顺序有关**，极端情况下会有城停在 -1。而新系统当前：

- `CompareForAssign` 用原始值排序 → **-1 会被排到 0 前面**（未定城被当成"比边境更优先"）；
- `CalcDevelopRingFactor` 把负数夹到下标 0 → 被当作"最前线"（×0.5）。

**建议改法**：把 `-1` 一律视为**最深层**（不享受前线优先、也不受战时减半）：

```cs
// DeploymentSolver.RingOf
return ring < 0 ? DeepRing : ring;          // DeepRing = 99
// CityEstablishment.CalcDevelopRingFactor
if (ring < 0) ring = table.Length - 1;      // 未定 → 按最深层
```

## K5. 顺带发现：`City._CheckBorder` / `_IsBorderCity` 是死代码

`City.cs:1110-1145` 的这两个静态方法（名字很像"圈层计算"）**全工程无调用者** ——
真正在用的是 `UpdateTurnInfo` 里的内联逻辑。容易误导后来者，可在清理阶段删除。

## K6. 现状与待办

- R1 / R2 都**尚未修**（当前新系统照原样读 `borderLine`）；
- 两处修法都很小（1 个新方法 + 4 处调用 / 2 处夹取），且不影响存档；
- 修 R1 会**改变港关的编制**（从"恒 ≥1 人"回到"按归属都市圈层 0~2 人"），属于决策 3 的原意。

**原实现的三个问题**：

```cs
while (hasNoCheckBorder)                       // ② 没有"本轮无进展"出口 → 极端数据下会死循环
{
    for (...)
    {
        ...
        int minBorder = 99;
        foreach (neighbor) if (neighbor.borderLine >= 0) minBorder = Mathf.Min(...);
        if (minBorder >= 0) c.borderLine = minBorder + 1;   // ③ 初值 99 也满足 >= 0 → 孤立城被写入 100 假圈层
        hasNoCheckBorder = c.borderLine == -1;               // ① 覆盖式赋值 → 可能提前退出，残留 -1
    }
}
```

**修复后**：

```cs
int maxRound = scenario.citySet.Count + 1;     // 轮数上限，兜底防死循环
int round = 0;
while (hasNoCheckBorder && round++ < maxRound)
{
    hasNoCheckBorder = false;                  // ① 每轮先清零
    for (...)
    {
        if (c == null || !c.IsAlive || c.BelongForce != this || c.borderLine >= 0) continue;
        int minBorder = 99;
        foreach (neighbor) if (neighbor != null && neighbor.borderLine >= 0) minBorder = Mathf.Min(...);

        if (minBorder >= 0 && minBorder < 99)  // ③ 必须真的找到已解析的相邻城
        {
            c.borderLine = minBorder + 1;
            hasNoCheckBorder = true;           // ① 只要本轮有进展就再跑一轮
        }
    }
}
```

要点：

- **有进展才继续**：一轮下来一座城都没解析出来 → 立即退出（不会空转，也不会死循环）；
- **不再写入假圈层 100**：找不到已解析的相邻城就不赋值（保持 -1）；
- **残留 -1 的兜底链路仍在**：`CityEstablishment.ResolveRing`（港关按归属都市）→
  `DeploymentSolver.RingOf`（-1 按最深层）→ `CalcDevelopRingFactor`（-1 取最后一档）。

# 附录 N：圈层算法改为多源 BFS + 港关范围明确

**改动来源（提问）**：① 计算圈层这里是不是不需要 `while`？② 是不是要判断 `IsCity()`？

## N1. 问题①：`while` 的必要性

| 方案 | 结论 |
|---|---|
| **直接删掉 `while`** | ✗ 不行：规则是 `ring = min(相邻城 ring) + 1`，解出圈层 k 需要圈层 k-1 已解；城市在 `citySet` 里的顺序是任意的，**一趟最多只解出圈层 1**，更深的全留在 -1 |
| **保留 while（反复扫全表）** | ✓ 结果正确，但最坏要扫"圈层深度"遍；且一轮毫无进展时既不推进也不退出 |
| **改成多源 BFS（已采用）** | ✓✓ 规则"离边境几跳"= 到最近边境城的最短跳数，与 BFS 等价；**一趟 O(n)、与顺序无关、不可能死循环** |

## N2. 问题②：`IsCity()` 判断（原来是"隐性排除"）

原代码把 `borderLine = -1` 的初始化包在 `if (c.IsCity())` 里 → **港关/关卡根本不参与圈层计算**，
`borderLine` 永远保持默认值 0（= 边境）→ 这就是附录 K 里 R1 的根因。

现改为**显式**处理：

```cs
// ① 相邻势力 / 邻城收集：仍然只对都市做（外交等模块依赖这个语义，保持不变）
if (c.IsCity()) { CityCount++; foreach (neighbor) { ...收集 NeighborForceList / NeighborCityList... } }

// ② 圈层初始化：明确只有都市参与；港关由 CityEstablishment.ResolveRing 按归属都市推导
if (c.IsCity())
{
    c.borderLine = -1;
    foreach (neighbor) if (!neighbor.IsSameForce(c)) { c.borderLine = 0; ringQueue.Enqueue(c); break; }
}
```

BFS 扩散时同样只走都市：

```cs
while (ringQueue.Count > 0)
{
    City cur = ringQueue.Dequeue();
    int nextRing = cur.borderLine + 1;
    foreach (neighbor of cur)
    {
        if (neighbor == null || !neighbor.IsAlive) continue;
        if (neighbor.BelongForce != this) continue;    // 只扩散自己势力
        if (!neighbor.IsCity()) continue;              // 港关不参与圈层
        if (neighbor.borderLine >= 0) continue;        // 已定
        neighbor.borderLine = nextRing;
        ringQueue.Enqueue(neighbor);
    }
}
```

| 3 | **港关恒为 0（边境）**，还会把相邻都市的圈层拉低（旧 while 读邻居 ring 时港关的 0 也算数） | 港关不写值、也不参与扩散；都市圈层不再被港关干扰 |

## N4. 若之后想"让港关有自己的圈层"

两处改：

这与决策 2（"需要发展的城市给予更多的开发人才"）直接冲突。

## Q3. F7：弹性岗位上限随"人力丰裕度"放宽

`CityEstablishment` 开发席位：

```cs
devSeat = round(devRaw × devModifier);

// 上限不再是死数字：
float abundance = clamp(人均城数 / staffPerCityBaseline, 1, staffAbundanceMax);
int devCap = max(devSeatMax, round(devSeatMax × abundance));
if (devSeat > devCap) devSeat = devCap;
```

| 参数 | 默认 | 含义 |
|---|---|---|
| `staffAbundanceScaling` | true | 弹性岗位是否随人力放宽 |
| `staffPerCityBaseline` | 8 | 人均城数达到此值按 1.0 倍计 |
| `staffAbundanceMax` | 2.5 | 最多放大倍数 |

判定依据用**势力自身**的 `CityCount` / `PersonCount`（取不到时回落到传入的 `personTotal`），
人力紧张的势力（如 28 城 50 人 → 1.8 人/城）行为**完全不变**。

原因链会打印上限与倍数，便于核对：`… 修正×0.72 上限8人(人力×2.5)`。

## R1. 后勤（Logistics）到底是什么

代码里的**后勤岗 = 后方城的「治安 + 粮草」兜底岗**（条件：`borderLine >= 2` 且治安/粮草吃紧）：

本轮把它**拆成两项各 1 人、上限 2**，原因链分别注明：

## R3. 决策② 军事岗放开

—— **基础编制是上限**，所以"永安 97k 兵只有 5 个军事岗"。

## R5. 决策④ 前线有权与内陆交换能力武将

```cs
ring = 调向更前线 ? crossRingCost × frontwardCostFactor(0.25)   // 便宜：鼓励前送
                   : crossRingCost × backwardCostFactor(1.5);    // 贵：抑制回撤与横跳
```

同时 `ResolveRing` 取代 `borderLine`（港关自身圈层恒为 0，原写法会把所有港关误当"前线"）。

2. **分配顺序**（`CompareForAssign`）→ 军事/守备岗按圈层 0 优先拿人；
3. **前送成本 0.25 倍**（本条）→ 内陆能力武将被优先匹配到前线，而不是被行程/跨圈层成本挡住。

# 附录 U：后续五项变更汇总（后方保底 / 动态基准 / CityAI 收口 / 前期优先登用 / 内政登用优先级）

## U1. 后方城保底人数（决策："后方城池最低留 1 到 5 人"）

**规则（2026-09-24 上调）**：`minSeatAtRearByLevel = { 2, 2, 3, 3 }`（小/中 2、大/巨 3），
生效圈层 `rearFloorMinRing = 1` —— **次前线（1）与后方（≥2）都受约束**；边境（0）交给军事保底。

> 变更原因：原表 `{1,2,3,5}` + 只约束圈层 ≥2，导致 ① 后方小城只保 1 人（内政/运输转不动），
> ② **次前线城可以被抽到 0 人**（完全没有保底）。这是"城池要保底 2~3 人维持最低运转"的修正。

| 城类型 | 保底来源 | 数值 |
|---|---|---|
| 次前线（圈层 1）/ 后方（≥2） | `CityEstablishment.MinRearSeats` | **小/中 2、大/巨 3** |
| 边境城（圈层 0） | `minMilitarySeatAtBorder` | 3（军事） |
| 港关 | `minPortGateGuard` | 1（守备） |

**两处生效（同一口径）**：

1. **编制保底**：单城上限截断**之后**，`运输 + 开发 + 后勤 < 保底` 时优先补**开发**（= 战略资源积累）；
   语义上"保底优先于上限"（保底 ≤5 人，刻意如此）。
2. **调动闸门**（`DeploymentExecutor.CanTransfer`）：源城为后方城时，`剩余人数 ≤ 保底` 即拒绝外调 —— 前线抽不动保底的人。

## U2. 后方保底动态基准（决策："按总人数/城池数 做基准兜底"）

```
人均      = 势力总人数 ÷ 势力城数
目标      = round(人均 × rearShareRatio(0.3))
后方保底  = clamp(目标, 等级下限{1,2,3,5}, 等级上限{3,4,6,8})
          再 min(…, 人均)          ← 关键：人少时不会强留，不饿着前线
```

| 势力规模 | 人均 | 后方 Lv1/2/3/4 保底 | 说明 |
|---|---|---|---|
| 196 人 / 9 城 | 21.8 | **3 / 4 / 6 / 7** | 人多 → 后方留得住（旧固定值仅 5） |
| 50 人 / 28 城 | 1.8 | **1 / 1 / 1 / 1** | 人少 → 被"人均"压回 |
| 320 人 / 20 城 | 16 | **3 / 4 / 5 / 5** | `0.3×16=4.8→5` 正确 |

回退：取不到势力规模 → 用固定值；`enableDynamicRearFloor=false` → 用固定值。
**与 `abundance`（弹性岗位）同基数**（都是人均城数），全系统口径统一。

**已知算术边界（重要）**：公式最后一步 `min(目标, 人均)` 会**压过**等级保底 ——
所以"每城至少 2 人"在**人少时不成立**：

| 势力规模 | 人均 | 新表 {2,2,3,3} 的实际结果 | 说明 |
|---|---|---|---|
| 196 人 / 9 城 | 21.8 | 3 / 4 / 6 / 7 | 人丰裕 → 保底放宽（上限 {3,4,6,8} 约束） |
| 50 人 / 28 城 | 1.8 | **1 / 1 / 1 / 1** | 28×2=56 > 50，算术上不可能；宁可后方瘦也不饿死前线 |

若要"无论人多少，每城至少 2 人"的**硬保底**（宁可前线少人），需要一个新开关让最后一步跳过
`min(目标, 人均)` —— 当前**未实现**，默认走软保底（推荐：先观察实际观感）。

# 附录 T：军事岗按"5000 人一队 + 副将"重算（前线人数保证）

## T1. 问题

旧公式 `milByTroops = ceil(预想兵力 × generalsPerTroop / 主将带兵上限)`：
永安 9.7 万兵 / 主将带兵上限 7040 → 14 队 → 但被 `baseSeat + ring + threat` 上限压到 5；
即使放开也只给 **9 人**（实测）—— 而"5000 人一队"应为 **18 队**，再加副将 **≈27 人**。

## T2. 新公式

```cs
perUnit    = troopsPerUnit(5000)；若主将带兵上限 < 5000 则按主将上限（队数更多）
unitCount  = ceil(预想兵力 / perUnit)
milByTroops= ceil(unitCount × (1 + deputyPerUnit(0.5)))
milSeat    = max(milByTroops, baseSeat+ring+threat, 前线保底(3))
milSeat    = min(milSeat, militarySeatHardMax(60))
```

| 参数 | 默认 | 含义 |
|---|---|---|
| `troopsPerUnit` | 5000 | 每队编制兵力 |
| `deputyPerUnit` | 0.5 | 每队平均副将（多人队伍） |
| `militarySeatHardMax` | 15 → **60** | 单城军事岗硬顶 |
| `minMilitarySeatAtBorder` | 1 → **3** | 前线保底（"前线人数一定要保证"） |
| `maxPostsPerPerson` | 1.0 → **1.4** | 军事放开后会挤掉内政岗，故放宽总量预算 |

## T3. 特技组合搭配（第一步）

`DeploymentSolver.FeatureNovelty`：候选拥有"**本城驻军还没有的特技**"时，军事/守备岗匹配分 +0.35
（`featureNoveltyBonus`）。目的：避免一座城堆满同类特技，无法组成互补的多人队伍。
**边界**：只做"多样性"，不做"队伍级 combo 判定"（后者需要出征编队的组队规则，属后续步骤）。
