# 剧本编辑器（Scenario Editor）

面向 Sango Infinity 工程 `Build/Content/Scenario/Scenario.json` 的可视化编辑工具。
浏览器端编辑 + 本地 Node 服务读写磁盘，支持桌面与手机浏览器。

## 快速开始

```bash
cd Tools/ScenarioEditor

# 1. 安装依赖（首次）
npm install

# 2. 开发模式：终端 A 启动后端（默认 3009），终端 B 启动前端（默认 5273）
npm run server
npm run dev
# 浏览器打开 http://localhost:5273

# 生产模式：构建后由后端一并托管
npm run build
npm run server
# 浏览器打开 http://localhost:3009
```

手机端访问：让手机与电脑处于同一局域网，用电脑内网 IP 替换 `localhost`
（例如 `http://192.168.1.10:5273`）。开发模式需要 `vite --host`，或直接使用
生产模式的 3009 端口。

## 环境变量（可选）

| 变量 | 说明 | 默认值 |
| --- | --- | --- |
| `PORT` | 后端服务端口 | `3009` |
| `SCENARIO_FILE` | 剧本文件路径 | `<工程>/Build/Content/Scenario/Scenario.json` |
| `COMMON_DIR` | 公共数据表目录 | `<工程>/Build/Content/Data/Common` |
| `LIBRARY_API` | 武将库网站地址 | `http://localhost:3001` |

## 功能一览

### 数据浏览与编辑
- **概览**：剧本基本信息（名称、描述、年份、地图类型等）、四类实体统计、校验状态、备份历史与一键回滚。
- **武将 / 都市 / 军团 / 势力**：四张独立列表，支持搜索、按势力筛选、仅看问题项、任意列排序、列显示自定义（本地持久化）。
- **公共数据**：编辑 `Build/Content/Data/Common` 下的全部 27 个数据表（见下文）。
- **详情面板**：按 schema 分组折叠，字段即时写入内存；支持显示/隐藏未定义字段、补全缺失字段、删除透传键、复制实体、上下条快速切换（`J` / `K`）。

### 弹窗宽度的一个坑（改动前必读）

shadcn 的 `DialogContent` 基础样式里带 **`sm:max-w-lg`（512px）**。如果只传 `w-[min(96vw,960px)]` 这类宽度，
会撞上两件事：

- `width` 与 `max-width` 不是同一个属性，光设 `width` 打不过它；
- 而且它只在 **≥640px** 生效 —— 所以窄屏（布局退化为纵向堆叠）看不出问题，**只有宽屏才会被截到 512px**。

结果就是库导入面板右侧详情栏固定占 340px，对话框却只有 512px，左侧武将列表只剩 150 出头，
武将名被挤成一个字。

好在 `cn()` 走的是 tailwind-merge：它会按「同属性 + 同变体」合并，
**只要显式传一个 `sm:max-w-[…]`，基础样式里的 `sm:max-w-lg` 会被直接从类名里删掉**，
不存在层叠先后之争。所以规则是：**给 DialogContent 设大宽度时，必须同时给一个 `sm:max-w-[…]`。**

> 侧滑面板（`SheetContent`）同理，基础样式是 `sm:max-w-sm`，现有的几处都已正确覆盖。

### 编辑约束

- **表头与数据共用一个水平滚动条**：表头是滚动容器内的粘性元素（`sticky top-0`），
  横向滚动只由底部那一条控制，表头与列永远对齐，不会出现两条滚动条不同步。
- **网格严格跟随内容宽度**：表格宽度 = 勾选列 + 各内容列 + 列间隔 + 操作列，**不拉伸到容器宽度**。
  右侧留白是干净空白，不会因为行线横穿空白区而看起来像多出一列空单元格。
- **页面底板不画网格**：`.app-shell` 只剩顶部光晕。原先还有一层 40px 的背景网格，
  但表格是透明的，网格会从数据缝隙里透出来，像「凭空多出许多列线」，
  而且它固定 40px、与真实列宽无关，永远对不上列边界。
- **数据区画 Excel 风格网格线**：行线跟在行高上、列线跟在 `columnWidth` 上，
  所以线一定与数据对齐。颜色用 `--grid-line`（比 `--border` 淡一档），是「分隔」不是「框」。
  实现上列线挂在单元格的包裹元素上并让它撑满行高（grid 默认 `stretch`），
  垂直居中交给包裹元素自己的 `items-center` —— 不能用 grid 的 `alignItems: center`，
  否则包裹层高度退化为内容高度，列线会在行与行之间断开。
- **列宽按内容自适应**：原先按字段类型给固定宽度（多数列统一 130px），
  「性别」这种只放一个字的列也占掉一整条，整张表又宽又稀。
  现在由 `src/lib/autoColumns.ts` 逐列取
  「表头所需宽度（标签 + 排序图标 + 内边距）」与「该列所有单元格文本所需宽度」的最大值，
  再用上下限夹住（`columnBounds`）：五维 / 适性 40~72px、数值 52~140px、
  姓名 72~190px、数组型 76~260px，另设 40px 绝对下限保证点得中。
  测量走 canvas 的 `measureText`（带缓存，重复值只测一次），
  850 行 × 18 列实测 **6ms**；宽度量化到 2px 网格以减少抖动。
  实测 18 列合计从 1690px 收到 1164px，表格总宽从 1954px 收到 1392px。
- **列间留白 6px**：没有间隔时相邻两列只靠各自的 `px-2` 隔开，
  「所属都市 / 所在都市」这类同名列会糊成一片。间隔用 grid 的 `column-gap` 实现，
  轨道宽度即列宽不变，所以文字不会被挤窄。
- **固定列宽里不放宽度不受控的控件**：下拉框（`SelectTrigger`）的基础样式是 `w-fit`，
  会按内容撑宽；表格里的引用下拉一度还写死了 `min-w-[150px]`，
  在 130px 的列里必然越界压到右列。规则是：**表格内的下拉一律由单元格接管宽度**
  （`w-full min-w-0 px-1.5`），文字靠 `line-clamp-1` 截断、完整内容放进 `title`；
  单元格容器再加 `overflow-hidden` 兜底。宽度默认值集中在 `RefSelect` 一处，
  用 `className` 覆盖（`cn` 走 twMerge，后者胜出），因此表单里的宽下拉不受影响。
- **Id 一律只读**：四个集合的 `Id` 列不可点击、不可编辑，详情面板里也不再出现该字段
  （标题栏已经显示）。Id 是集合键，改了会直接破坏「键 == Id」的约定并让引用失效。
- **武将与城池不允许新增 / 删除**：这两类数据分别由武将库与地图决定，
  误删会破坏剧本，因此界面上不提供新增按钮、删除按钮置灰，store 层也做了兜底拦截。
  「从武将库导入」仍然可用（那是显式的导入动作，不是随手新增）。
- **新建优先使用最小空闲 Id**：`computeNextId` 从「最大 Id + 1」改为「从 1 起找第一个未占用的 Id」。
  删除军团 / 势力后空出的 Id 会立刻回到可分配池，下一次新建就会用上，不浪费编号。

### 名称转换（把 ID 显示成人能看懂的名称）
剧本里大量字段存的是「别的表的 ID」。表格与详情面板会统一把它们渲染成名称，并提供下拉选择：

| 字段 | 显示 |
| --- | --- |
| `BelongForce` | 势力名（势力在剧本里没有名称，由**君主名**推导） |
| `BelongCorps` | 军团名（由**军团番号 + 军团长**推导） |
| `BelongCity` / `CurrentCity` / `NeighborList` | 都市名 |
| `Father` / `Mother` / `Brother` / `SpouseList` / `LikePersonList` / `HatePersonList` | 武将名 |
| `Governor` / `Counsellor` / `Comander` | 武将名 |
| `Official` | 官职名（来自 `Officials.json`） |
| `personality` / `argumentation` | 性格 / 义理名 |
| `spearLv` 等六项适性 | 适性档位（Ｃ/Ｂ/Ａ/Ｓ/Ｓ１…，来自 `AbilityLevelTypes.json`） |
| `birthplace` / `province` | 州名 |
| `BuildingType` / `CityLevelType` | 建筑类型 / 都市规模名 |
| `Flag` / `Title` | 旗帜 / 爵位名 |
| `FeatureList` / `Techniques` / `InitTechniques` | 特技 / 技巧名 |
| `wordTac`（舌战话术） | 大喝 / 诡辩 / 无视 / 镇静 / 激昂（`Rhetoric` 枚举） |
| `appoint`（军团委任） | 无 / 攻略势力 / 攻占城池 / 自动（`AppointType`） |
| `itemStore`（库存、随身物品） | `存放类别×数量`，如「枪×5000」 |
| `EquippedWeapon` / `EquippedHorse` / `EquippedArmor` | 物品名，`-1` 显示为「无」 |
| `0` 且标记 `zeroMeansNone` 的引用 | 统一显示为「无」 |

数组型引用（配偶、特技、相邻都市、库存…）不再是手敲逗号数字，而是「按名称勾选 / 选择 + 数量」的弹层，
并保留「手动输入」入口以便批量粘贴或填写候选表以外的 ID。单元格悬停时会显示 `名称 (Id)` 便于核对原始值。

### 表格里的颜色编码

颜色只用来「扫一眼就能定位信息」，因此只在有明确含义的地方使用，且不与状态色冲突：

- **势力旗帜色**：所有指向势力的字段（武将 / 都市 / 军团的 `所属势力`）前置一个色点，
  颜色取自该势力的 `Flags.json` 的 `color`，与游戏里旗帜颜色一致。
  快速回答「这一片是谁的」，也便于在势力页按颜色核对归属。
- **五维评级色**：五维（统率 / 武力 / 智力 / 政治 / 魅力）按数值分级着色
  —— `≥95` 红、`≥90` 暗金、`≥80` 紫、`≥70` 蓝、`≥60` 绿，`<60` 保持默认色。
  当前剧本统率 ≥95 的只有 11 人、90~94 有 18 人、低于 60 的有 425 人，
  因此高值那一小撮会被立刻挑出来，低值不会变成一整片彩色噪声。
- **兵种适性档位色**：六项适性（枪 / 戟 / 弩 / 骑 / 水 / 兵器）按档位着色
  —— `Ｓ`（含 Ｓ１〜Ｓ４）红、`Ａ` 紫、`Ｂ` 绿、`Ｃ` 保持默认色。
  判定依据是**档位名称**而不是档位 Id，因此 `AbilityLevelTypes.json`
  以后新增档位能自动继承配色，也不用改代码；全角 `ＳＡＢＣ` 与半角 `SABC` 都认。
  颜色与五维评级色同源（红 = 最强、紫 = 强、绿 = 中等），所以同屏看到红色
  无论是「统率 95+」还是「骑兵适性 Ｓ」，含义都是「最强档」。
- **优先级**：字段有校验错误 / 警告时，**状态色优先于评级色**——
  「数值高但有错」时更需要先看到问题。

**被游戏忽略的字段会明确标注。** 剧本与公共数据表里有一批「JSON 里有、C# 类里没有」的旧键
（`horse` / `left_weapon` / `right_weapon` / `ketsuen` / `wajutsu`、`Force.allies` / `Force.like`、
`City.specialty`、`JobTypes.linkBuildingKind`、`ItemType.subKind` …），它们反序列化后会落进
`JsonExtensionData` 且无人读取。编辑器把这些字段的标签加上「（旧键）」并在悬停提示里说明当前不生效，
同时给出真正生效的替代字段（例如装备要写 `EquippedWeapon` / `EquippedHorse` / `EquippedArmor`）。

> 注意：`itemStore` 的键是 `ItemTypes.storeKind`（存放类别），**不是物品 Id**。
> 冲车与木兽共用 6、井阑与投石共用 7、三种船共用 8。因此编辑器按类别显示，
> 并对剧本中出现的非法类别（例如键 11，代码里 `ItemStoreKindType` 只到 8）给出校验警告。

### 公共数据（Common 目录）
把 `Build/Content/Data/Common` 下 26 个 json 作为一个可编辑的大项（`PersonLibrary.json` 已隐藏，见下）：

- 左侧按业务分组（武将与人材 / 兵种与战斗 / 都市与生产 / 科技与能力 / AI 与行为）列出文件与条目数；
- 右侧按文件结构**自动选择视图**：
  - 记录表（`Provinces`、`Features`、`Skills`…）→ 可搜索、排序、虚拟滚动的表格，单元格内联编辑；
  - 键值配置（`AIConfig`、`Personalities`…）→ 按顶层分组折叠的键值表单，支持嵌套对象与数组；
  - 值列表 / 记录数组（`RecommendedTroopTeams`、`duelPersonBehaviour`…）→ 可直接增删条目；
- 一个文件含多个分区时（如 `ai.json` 的 `Officials` 与 `ai`）顶部提供分区切换；
- **会标注被游戏忽略的内容**：`ai.json` 的 `ai` 分区顶层键不对应 `ScenarioCommonData` 的任何属性，
  加载时会被整体丢弃（改这里不生效）；该文件的 `Officials` 分区与 `Officials.json` 写入同一张表，
  重复定义时以加载顺序靠后者为准，界面会给出提醒；
- **数组引用区分两种语义**：`TroopTypes.skills` 这类是「元素即引用」，`TroopTypes.moveCost` 这类是
  「按 TerrainType.Id 逐项索引」，后者显示为「地形名 = 值」，不会把值误当 ID 去查名称；
- **能力下标**（`Techniques.needAttr`、`BuildingTypes.effectAttrType`、`TroopTypes.influenceAbility`）
  按 `Person.GetAttribute` 的 0 统率 / 1 武力 / 2 智力 / 3 政治 / 4 魅力 显示，而不是误用 `AttributeChangeTypes`；
- **注释与排版完整保留**：含注释的 `AIConfig.json` / `Personalities.json` / `RecommendedTroopTeams.json`
  采用「原文 + 最小差异」策略（`jsonc-parser` 的 `modify`），改动哪个值就只替换哪个值，
  注释、空行、字段顺序、缩进、换行符都不受影响；
- 对象形态的数据表里修改 `Id` 会自动同步集合键，保持「键 == Id」的文件约定；
- 每次保存前自动备份（最多 40 份），支持按文件回滚；写入前做语法校验、冲突检测；
  给原本不含注释的文件加注释会被拒绝，避免游戏侧解析失败。

### 公共数据的下载与差量补丁

公共数据改完之后，交付方式有三种，按「需要发多少东西」区分：

| 方式 | 内容 | 适合场景 |
| --- | --- | --- |
| **下载** | 该文件的完整内容（含注释与原始缩进） | 交付单表，或做整体备份 |
| **差量** | 只含改动字段的补丁 | 只改了几个值，不想发上万行 |
| **全部差量** | 所有「有基准且有改动」的文件合并成一个 JSON | 一次交完整批修改 |

**基准版**由管理员上传（`server/baseline/`），全体用户共用同一份，是差量计算的参照：

- 「把当前全部登记为基准」一次性快照整个 Common 目录，这是管理员最常用的操作；
- 也可以只把当前打开的那一个文件登记为基准；
- 清单里每个文件都标出「一致 / 有改动」，普通用户也能看到自己动了哪些；
- 差量计算**不做 zip**，是为了不给项目引入压缩库依赖；合并 JSON 对新旧消费方都更简单。

**差异规则刻意保持简单可预测**：

- **对象递归**：逐键比较，只输出真正变化的键（新增的键按「变化」处理）；
- **数组与标量整体替换**：数组只要有一个元素不同就整段输出。
  逐元素 diff 在插入/删除时索引会错位，得不偿失；而公共数据表的主流形态是
  「以 Id 为键的对象」（`Features` / `Provinces` / `Skills`…），对象递归已覆盖绝大多数实际改动。

补丁形态：

```jsonc
{
  "_meta": { fileName, generatedAt, baseRevision, baseAt, fileRevision, changed, removed },
  "data": { /* 只含改动字段、保留原始层级 */ },
  "removed": [["Features", "12", "name"]]   // 被删掉的路径
}
```

被删掉的字段用**路径数组**而不是 `a.b.c` 这样的点号拼接 —— 键名本身可能含点号，
拼接会产生歧义（已作为边界用例覆盖）。

实测：`Features.json`（52112 字节）只改一个 `Id` 时，补丁 **344 字节**，压缩 **99.34%**，
差异树内容为 `{"Features":{"1":{"Id":2}}}`，同层其它字段零泄漏。

「差量」按钮走 fetch 而非 `<a download>`：后端用 `204` 表示「没有改动」、`409` 表示
「还没有基准」，这两种都不是文件，直链会把错误 JSON 存成文件；走 fetch 才能给出明确提示。

### 都市地图

都市都带 `x` / `y` 两个整数坐标（当前剧本 87 座，范围 `33~215 × 44~219`，互不重叠），据此提供两条入口。

**地图表现**

- **形状区分建筑类型、颜色同步所属势力**：
  - 形状：**都市=方形**、**关所=圆形**、港=菱形（按类型名称匹配，换 Id 也不受影响）；
  - 颜色：一律取「所属势力 → 旗帜 → `Flags.json` 的 `color`」，与游戏里旗帜颜色一致。
    因此**都市 / 关所 / 港都跟随势力颜色**，同一势力的所有城市颜色相同，
    一眼能看出某片区域属于谁；**无归属势力（`BelongForce = 0`）为纯白**，
    并始终保留深色描边，保证在亮色主题下白点依然可见。
  - 形状取自 `BuildingTypes` 的**名称**而不是写死 Id，数据表调整后仍然正确。
- **城池名常驻标注**：名称带底色小片，任何底色上都读得清。默认开启**避让**——按
  「选中 > 悬停 > 相邻多 > 驻军多」排序后贪心放置，与已放置名称重叠的跳过；因此低缩放下
  地图依然干净，放大后名称自动补齐（工具条可关闭避让，强制显示全部）。
- **标记放大 3 倍**：直径 = 格子边长 × 1.56，钳制在 12~46px 并随缩放变化。
  颜色 + 形状双编码区分建筑类型（圆=都市 / 方=关所 / 菱=港）。
- **画布尺寸动态计算**：`max(可视区尺寸, 坐标范围 × 格子 + 留白)`。小图铺满窗口，
  大图（坐标范围更大时）完整展开并可滚动，后续换更大的地图不需要改任何常量。
- **两种连线**：
  - **相邻连线**（实线）：来自 `NeighborList`，只画一次不重复；
  - **归属连线**（虚线）：关所 / 港 → 所属都市，来自 `BelongCity`。实测 45 个关所与港
    全部有 `BelongCity`，且都指向 `BuildingType=1` 的都市，距离 5~36 格（平均 12.6）。
    之前关所与港在图上是孤立的，现在能看出它们挂在哪座城下。
  - 选中任一端时相关连线高亮为 Primary 色。

`PersonLibrary.json`（内置武将库）**不出现在公共数据列表中**：

- 它是 1.2MB / 833 条，全量解析一次清单要花掉大部分时间；隐藏后 `/api/common` 的清单解析

隐藏只影响列表：按文件名直接调用接口仍可读写该文件，且武将库接口走的是
`Build/Content/Data/PersonLibrary.json` 这条独立路径，不受影响。
要改回来，删掉 `server/lib/commonFiles.js` 的 `HIDDEN_FILES` 与
`src/lib/commonMeta.ts` 中 `PersonLibrary.json` 的 `hidden: true` 即可。

### 部署模式与账号

由环境变量 `WORKSPACE_MODE` 决定数据落在哪里：

| 模式 | 未登录 | 登录后 |
| --- | --- | --- |
| `local`（默认） | 直接读写**工程目录**，与单机用法完全一致 | —— |
| `multi` | **只读游客**：能浏览、下载、套用模板，不能保存 | 读写 `server/workspaces/<用户名>/`，各改各的互不影响 |

之所以用显式开关而不是「有密钥就自动多用户」，是因为开发机上密钥文件本来就在，
自动切换会让本地保存悄悄写进工作区、看不到工程目录的变化。

**账号复用武将库网站（`Tools/PersonLibraryWeb`），不引入第二套身份。**
网站用的是 HMAC 签名的自包含令牌：

```
token = base64url(JSON{u, exp}) + '.' + base64url(HMAC-SHA256(secret, payload))
```

编辑器直接读网站的 `data/.token-secret` 与 `data/accounts.json` 独立校验，
**不依赖网站是否在线，也没有任何跨服务调用**。令牌载荷里只有用户名与过期时间、
没有角色，角色一律以 `accounts.json` 的实时数据为准 —— 所以改角色不需要重新登录。

角色沿用网站的体系：`guest(0) < editor(1) < admin(2) < super(3)`，
**管理员 = admin / super**，可上传模板与剧本。登录由后端代理转发网站的
`/api/auth/login`，浏览器不必处理跨域。

### 线上部署

线上地址 `http://139.155.98.66/scenario/`，与创意工坊（站点根路径）、
武将库（`/personlib/`）同机，三者由同一个 nginx 站点提供。

**子路径适配由三处配合完成**（换部署路径时必须同步改这三处）：

| 位置 | 作用 |
| --- | --- |
| `.env.production` 的 `VITE_API_PREFIX=/scenario` | 让前端接口与下载直链带上前缀，统一在 `src/lib/api.ts` 的 `withApiPrefix` 里拼接 |
| `vite.config.ts` 的 `base`（生产为 `/scenario/`） | 让 `index.html` 里的 assets 写成绝对路径 |
| `deploy/nginx-scenario.conf` | 剥掉 `/scenario` 前缀再转发给后端 3011 |

后端**完全不感知子路径**：静态目录与 SPA 回退正则都按根路径写，
所以 nginx 用带尾斜杠的 `proxy_pass http://127.0.0.1:3011/` 剥掉前缀即可。
下载类直链的前缀也补在 `withToken()` 里而不是各调用点 —— 否则漏掉一处就会在线上静默 404。

**目录约定不能随意改。** 后端 `server/lib/paths.js` 用「脚本所在目录上溯两级」
定位工程根，因此线上必须摆成与本地开发相同的结构：

```
/opt/sango-scenario/                       ← 后端眼中的工程根
├── Build/Content/                         ← 游客可见的参考剧本 + 公共数据表
└── Tools/
    ├── ScenarioEditor/                    ← 本工具（server/ 与 dist/）
    └── PersonLibraryWeb/server/data/      ← 账号文件（软链到同机武将库）
```

账号文件用**软链**指向 `/opt/sango-personlib/server/data/`，保证「一处改密码两边同时生效」，
也避免密钥被复制成两份而产生不一致。启动日志会打印实际生效的数据目录、工作区模式与账号来源。

**部署步骤**（部署包 = `Build/` + `Tools/` + `deploy/`）：

```bash
# 1. 本地构建（会把 /scenario 前缀写进产物）
npm run build

# 2. 打包上传后，在部署包根目录执行
bash deploy/deploy.sh
```

脚本依次完成：构造工程根与账号软链 → 暂存线上运行期数据
（`server/workspaces`、`server/templates`、`server/baseline`、`server/backups`）
→ 同步代码与 `Build/Content` → 还原暂存 → 安装生产依赖
→ PM2 重载（`sango-scenario`，端口 3011）→ 安装 nginx 片段并重载 → 健康检查。

`server/workspaces` 里是**玩家各自的工作区**，部署包中的同名目录只是开发机样例，
脚本用「暂存—同步—还原」保证它们不被覆盖；`Build/Content` 则随部署包更新
（它是只读的初始数据，玩家改动都落在各自工作区里）。

**nginx 片段靠扩展点加载。** 主站点配置（ModHub 部署时生成）里有一行
`include /etc/nginx/conf.d/sango-sites/*.conf;`，本工具的片段装到该目录。
这样 ModHub 每次重新部署重写主配置时，不会把剧本编辑器的 location 冲掉 ——
这也是为什么片段独立成文件、而不是直接写进主配置。

### 与另外两站的互链

三个站点（剧本编辑器 / 武将库 / 创意工坊）互为入口：每个站点的导航里都能跳到另外两个，

| 变量 | 本地开发（`.env`） | 线上构建（`.env.production`） |
| --- | --- | --- |
| `VITE_WORKSHOP_URL` | `http://localhost:5173` | `http://139.155.98.66/` |
| `VITE_PERSON_LIB_URL` | `http://localhost:5174` | `http://139.155.98.66/personlib/` |

窄屏下顶栏只保留图标，文字换成 tooltip，避免工具条被撑高换行。

### 剧本模板库

模板是「一份完整的 `Scenario.json`」，由管理员上传后存在服务端、全体共享；
用户挑一个套用，内容复制到自己的工作区，之后的修改不影响他人。

- 入口在顶栏「模板库」，同一个对话框里也完成登录与上传；
- 目录结构 `server/templates/<id>/{Scenario.json,meta.json}`，`id` 用
  `时间戳_随机串` 生成（天然有序且不会撞名），中文名与说明放 `meta.json`；
- 列表只读 `meta.json` 的汇总（实体数量等），**不会为每一行去解析 1.7MB 的剧本**；
- 套用 / 上传覆盖时会先把原文件另存为 `.bak`，已有剧本时必须显式 `force` 才覆盖，
  前端会先弹二次确认，覆盖后还可从「概览 → 备份历史」回滚；
- 上传剧本走 `text/plain` 直发原始 JSON，**避免 1.7MB 内容被二次转义**；
- 下载走浏览器直链，令牌以 `?token=` 传递（`<a download>` 无法自定义请求头）。

### 武将源接入
- 「从武将库导入」：从武将库网站（`Tools/PersonLibraryWeb`，默认 3001）拉取武将并追加进 `personSet`；
  若库中 Id 已被占用会自动分配新 Id，避免覆盖。
- 详情面板中的「武将库回填」：按分组（姓名、五维、适性、人际、特技…）把库中数据回填到剧本里的指定武将。
- 数据来源降级链：**武将库网站接口 → 网站本地数据文件 → 游戏内置武将库**，任一环节不可用都不影响使用。

### 校验
四层检查，问题分「错误 / 警告 / 提示」三级，可在「校验」页签按级别与集合筛选，点击直接跳转定位：
1. **结构**：集合同步键名与 `Id`、非数字类型。
   **字段缺失一律按默认值载入、只给警告，不报错误** ——
   游戏侧（Newtonsoft）对缺失字段本来就取类型默认值（数值 0、引用 0、字符串 null），
   旧剧本与第三方模组少几个键是常态；若按错误处理，这些噪声会把真正的问题淹没。
   唯一的例外是 `Id`：它同时是集合的键，缺失会让实体无法定位与保存，因此仍按错误处理。
2. **取值**：数值区间、枚举候选表、数组长度与元素范围（五维 `[基础值, 成长类型]`、适性 `[等级]`、`body` 8 位、`itemStore` 成对等）。
3. **引用**：势力 / 军团 / 都市 / 武将 / 特技等引用是否存在于本剧本。
4. **一致性**：武将–军团–势力的归属链条、君主与军团长的归属、登场年与生卒年的先后、都市相邻关系双向性、死亡武将仍有归属势力、重名武将、未知字段（如原版残留的 `stateName?`）。

> 说明：官方剧本中少量武将的 `Father` 指向 Id ≥ 1000 的占位引用（剧本与武将库中均不存在），
> 这类问题按「警告」提示并附解释，不计入错误，以免淹没真正的问题。

> `imageID` 是游戏侧已标记「弃用」的旧立绘 ID，现行字段是 `image`（暴击图）与
> `image_old`（老年暴击图）。它普遍存在于旧数据里（当前剧本 850 个武将人手一个），
> 因此被列入 `DEPRECATED_KEYS`：既不进字段表、也不参与未知字段提示，
> 免得校验页被 850 条同类信息刷屏。数据本身**原样保留并写回**，
> 需要查看或清理时，实体详情面板的「未定义的透传字段」分组里列得出来。

### 备份：增量存储

剧本单份 1.67 MB，原先每次保存全量复制一份、保留 60 份 ——
**单个用户的工作区光备份就能堆到 100 MB 量级**，上云后这是持续增长的存储成本。
现在改为**链式增量**

- 每份备份要么是 **full**（`Scenario.json` 原文），要么是 **delta**（`delta.json`，相对**前一份**的扁平差异）；
- 每条 delta 只包含「这一次保存改了什么」，所以最小；
- 保留份数 60 → **10**；
- delta 超过全量的 60% 时改存 full —— 补丁比原文还大就没意义了；
- 老备份没有 `kind` 字段，一律按 full 读取，**升级后旧备份仍可正常还原**。

**为什么是链式而不是「锚点式」**（每条 delta 相对最近的全量锚点）：
锚点式创建与恢复都只需一次差异应用，但每次清理掉最老的锚点时，
**依赖它的那一批 delta 全部要被重建成全量**。实测锚点间隔 5、保留 10 时，
10 份里有 6 份是全量，**只省 52.9%**；链式下清理只会让下一条重锚定，
代价恒为 1 份，实测**省 94.4%**。

创建时不需要重放链：上一次 `createBackup` 的入参内容就是前一份备份的内容，
进程内缓存一份即可零成本算差异；缓存未命中（如刚重启）时保守落全量。
恢复时需要重放链，但保留份数只有 10，实测重放成本在几十毫秒量级。

实测（真实剧本 1.67 MB）：

| 操作 | 耗时 | 占盘 |
| --- | --- | --- |
| 创建一份增量备份 | 20 ms | **< 1 KB**（只改 1 个字段时） |
| 还原该备份 | 10 ms | —— |
| 清理（keep=10） | 1.4 ms | —— |

**踩过的两个坑**（都会导致「删错备份」，值得记下来）：

1. 备份名早期实现是「从 1 开始找第一个不存在的名字」，于是清理掉 `auto_TS` 之后，
   同一秒内新建的备份又叫 `auto_TS` —— 而字符串序里 `auto_TS < auto_TS_9`，
   它会被排在最后**当成最老的一份**，下一次清理就把**刚存完的备份**删掉了。
   改为「取同秒内最大序号 + 1」，名字只增不减。
2. 排序不能直接用字符串比较：序号是数字，字典序里 `_11 < _9`，
   第 11 份会被排到第 9 份后面。改为解析出 `(时间戳, 序号)` 后按数值比较。

两处都补了回归断言（「最新创建的备份必须仍在保留列表里」「同时间戳内按序号严格递减」）。

### 安全与性能
- **保存前自动备份**，最多保留最近 60 份；支持从任意备份回滚。
- **冲突检测**：若磁盘文件被外部（如游戏 / 编辑器）修改过，保存会被拒绝，避免覆盖他人改动。
- **写回格式**：`2 空格缩进 + CRLF`，与游戏侧 Newtonsoft 输出一致；无改动时写回与磁盘字节完全相同。
- **虚拟滚动**：850+ 武将、上千条校验问题均只渲染视口内的行。
- **不可变更新 + 结构共享**：撤销 / 重做仅克隆被改动的实体，1.7MB 的剧本也能保持流畅。
- **延迟校验**：校验使用 `useDeferredValue` 在浏览器空闲时计算，不阻塞输入。

### 手机端

- **表格 <768px 自动切换为卡片列表**，触摸目标加大。
- **页签换行而不是横向滚动**：手机上不存在可见的滚动条，`overflow-x-auto` 会把右侧的
  「公共数据 / 校验」完全藏起来且没有任何提示，用户根本不知道还能往右划。
  改为 `flex-wrap` 后无论屏幕多窄，每个页签都看得见；小屏下同时隐藏页签图标、
  收紧内边距，让 7 个页签尽量少占一行。
- **工具栏同样使用换行**，避免按钮被挤出可视区。
- 顶部按钮在窄屏下自动降级为纯图标（如 `Ctrl K` 按钮、保存按钮的文字），
  标题与剧本名用 `truncate` 收缩，保证操作区始终完整可见。

## 扩展字段

- 剧本字段：改 `src/lib/schema.ts`，表格列、编辑表单、批量编辑项、校验规则与搜索索引
  全部由该文件驱动，无需改动其它代码。
- 公共数据表字段：先在 `src/lib/commonMeta.ts` 的 `COMMON_FIELD_LABELS` 里补中文标签，
  再在 `COMMON_FIELD_REFS` / `COMMON_ARRAY_ITEM_REFS` 里声明引用关系即可获得名称转换与下拉选择；
  即使什么都不加，通用编辑器也能正常浏览与编辑（标签回退为原始英文键名）。
- 新增 Common 目录下的 json 文件：服务端会自动列出（归入「未登记」分组），
  在 `COMMON_FILE_META` 里补一条即可获得中文名、分组、说明与新增模板。
