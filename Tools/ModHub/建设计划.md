# Sango Infinity 创意工坊（Sango Workshop）建设计划

> 目标：照 **Steam 创意工坊** 的信息架构与交互心智，为《Sango Infinity》搭建模组工坊网站。
> 范围（已确认，不越界）：**存储 + 分类展示 + 订阅/下载**。
> 视觉：Steam 的布局与信息架构，套三国水墨鎏金皮肤。
>
> 代码工程根目录：`d:/sango_infinity/Tools/ModHub/`

---

## 0. 一句话结论

书店 vs 图书馆的区别：普通下载站是"下载 zip，自己解压到 Mods"，玩家不知道有没有新版本、要不要重装；
**Steam 创意工坊是"点一下订阅，剩下的由客户端负责"**——持久订阅、自动更新提示、明确的"有更新/已安装/未启用"状态。

好消息：**Sango 现有机制离这个只差一步。**
`Mod.HasNewVersion()`（本地 `mod.info` 的 version vs 市场 `version` 比对）**已经实现了**，只是没被任何 UI 用起来；`GitDownloader` + `{id}@{version}.zip` 协议就是一个天然的分发通道。
本网站要做的，是补上 Steam 里"服务端知道谁订阅了什么"的那一层。

## 1. Steam 概念 ↔ Sango 现有机制映射表

| Steam 创意工坊概念 | Sango Workshop 对应 | 依托的游戏侧既有机制 |
|---|---|---|
| App ID | `sango_infinity` | `GameVersion.CurrentVersion` |
| Workshop Item / PublishedFileId | 模组的 `id`（`mod.info` 的 `id`） | 已是目录名与唯一主键 ✓ |
| 文件详情页 `sharedfiles/filedetails/?id=` | `/sharedfiles/filedetails/?id={id}` | 纯前端路由，顺带致敬 Steam ✓ |
| **Subscribe 订阅** | 下载到 `Mods/{id}/` 并写入启用列表 | `GitDownloader` + `Mod.Download()` + `modList.txt` ✓ |
| Unsubscribe 退订 | 删除该模组目录 | `ModManager.RemoveMod()` ✓ |
| **Out of date / Updated 有更新** | 本地 version < 最新版本 | **`Mod.HasNewVersion()` 已实现** ✓ |
| **Subscribed items 订阅的物件** | 我的订阅清单 + 状态 | 需新增：客户端上报本地安装清单 |
| Required Items 必需前置 | `mod.info` 的 `depends` | 已解析，做静态展示 ✓ |
| Change Notes 变更日志 | 版本更新说明 | 新增 `ModVersion.changelog` |
| Tags 标签 | 分类标签（剧本/武将/头像/语音/技能/UI） | Steam式多标签筛选，新增 |
| Awesomeness / 好评 | 好评计数 + 订阅者数 + 浏览数 | 新增（计数型，非功能性） |
| Add to Collection 合集 | —— | **本期不做**（见 §3.0） |
| UGC 自动后台更新 | 启动/打开时批量检查 + 一键更新 | `UIModManager` 增加按钮 ✓ |

> 三个概念天然对得上（ID / 订阅 / 更新检测），**说明这个方向没有和现有架构打架**，这是选 Steam 作为参照的最大理由。

## 2. 现状调研（游戏侧事实清单）

### 2.1 目录约定

| 路径常量 | 代码位置 | 实际落盘（发行包） | 作用 |
|---|---|---|---|
| `Path.ContentRootPath` | `Framework/IO/Path.cs` | `Build/Content/` | 游戏本体内容 |
| `Path.ModRootPath` | 同上 | `Build/Mods/` | **第三方模组根目录（= 全部"已订阅"内容）** |
| `Path.CustomEditRootPath` | 同上 | `Build/CustomEdit/` | **玩家自建内容（= 待发布素材）** |
| `Path.SaveRootPath` | 同上 | 游戏根目录 | 存档 |

`Build/CustomEdit/` 实际内容：

```
CustomEdit/
├─ Data/CustomPerson.json      ← 游戏内"编辑武将"产出的自建武将库（ID 20001+）
├─ Data/CustomPerson - 副本.json
└─ Scenario/Scenario{n}.json   ← 游戏内"编辑剧本"产出的自建剧本
```

依据 `Game/GameCustomEdit.cs`：
- 本体武将 ID `1–10000`
- Mod 武将 ID `10001–20000`（读各 Mod 的 `Data/CustomPerson.json`）
- 玩家自建武将 ID `20001+`（`SelfScenarioAddon.Load(Path.CustomEditRootPath + "/Data/CustomPerson.json")`）
- 自建剧本保存位置 `{CustomEditRootPath}/Scenario/Scenario{自增id}.json`（`Game/System/Game/ScenarioEdit.cs`）

> ✅ 印证了"上传默认以 CustomEdit 为内容"：玩家编辑出来的武将包 + 剧本包，天然就是一个可直接发布的工坊物品。

### 2.2 单个模组目录规范（已订阅/已安装态）

```
{ModRootPath}/{ModDirName}/
├─ mod.info                ← 【必需】没有它 LoadMod() 直接返回 null
├─ poster.jpeg             ← 封面（mod.info 的 poster 字段指定）
├─ Data/                   ← 通用配置 + 武将 + 技能
│   ├─ Common/*.json        （官职/兵种/AI…，递归枚举叠加）
│   ├─ CustomPerson.json    （Mod 武将库）
│   ├─ FaceConfig.json      （头像 ID 区间）
│   ├─ MediaData.json       （语音音效映射）
│   └─ Skill/Skills.json, Buffs.json
├─ Scenario/*.json         ← 剧本（ID 自动 count+id 偏移防冲突）
├─ Language/*.json         ← 多语言
├─ Assets/                 ← 散装资源（Face/*.png、Sound/*.OGG…）
└─ Package/{platform}/*.pkg← AssetBundle 资源包
```

### 2.3 `mod.info` 格式（关键）

`Game/Mod/ModManager.cs: LoadMod()` —— **INI 风 `key=value` 纯文本**，不是 JSON：

```
id=official_rp
name=官职扩展
description=让AI给了一版官职数值,可以试试
version=1.0
author=
depends=
poster=poster.jpeg
```

支持的 key：`id / name / description / version / depends / poster / assembly / author / size`。

⚠️ **必须规避的坑**：

1. 解析用 `s.Split('=')` 且只取 `c_v[1]` → **值里不能出现 `=`**，否则被截断。上传必须校验。
2. `size` 单位为字节。
3. `Tag` 在 `Mod` 类里存在，但 `mod.info` **没有**对应解析分支 → 标签只能作为网站侧元数据。

### 2.4 远端市场协议（网站必须兼容的核心）

`ModManager.NetModMarket / NetModInfo`，市场清单是 **JSON**（文件叫 `mod_list.txt`）：

```json
{
  "name": "市场名字",
  "url": "市场URL开头",
  "mods": [
    { "id":"official_rp", "name":"官职扩展", "version":"1.1", "size":88716,
      "auther":"ai", "description":"让AI给了一版官职数值", "poster":"poster.jpg" }
  ]
}
```

⚠️ 作者字段在协议里拼作 **`auther`**（历史拼写错误），必须原样输出，否则游戏内作者栏为空。

下载 URL 规则（`NetModMarket.MakeUrl`）：

```
url = market.url，若以 "/mod_list.txt" 结尾则截掉这 13 个字符
直链 = {url}/{id}@{version}.zip
```

`Mod.Download()` 流程：

```csharp
App.Instance.StartCoroutine(GitDownloader.DownloadAndExtract(Url, ModManager.MOD_ROOT_DIR,
    p => loadProgress = p,
    r => ModManager.Instance.UpdateMod($"{r.ExtractTargetPath}/{Id}", this)));
```

🔑 **上传包的硬性 zip 布局**：解压到 `Mods/` 后还要再拼一层 `/{Id}`，故 **zip 内必须有顶层目录，名字等于 id**：

```
official_rp@1.1.zip
└─ official_rp/
   ├─ mod.info
   ├─ poster.jpeg
   ├─ Data/…
   └─ Scenario/…
```

zip 若无顶层目录，`UpdateMod` 找不到 `mod.info` → "下载成功但列表里不显示"，最容易踩的坑。

### 2.5 ⚠️ 两个同名不同义的文件（`Mods/modList.txt` vs `mod_list.txt`）

这是 Steam 化设计时必须分清的：

| 文件 | 位置 | 含义 | 读写的 API |
|---|---|---|---|
| `modList.txt` | 客户端本地 `{ModRootPath}/` | **启用清单**：一行一个 mod.id，**行序 = 加载优先级** | `ModManager.LoadModList()` / `SaveModList()` |
| `mod_list.txt` | 服务端提供 | **市场清单**：该市场有哪些模组可下载 | `AddMarketFromUrl()` / `NetModMarket` |

→ 决定用途拆分：**"是否订阅"看本地目录是否存在，"是否启用"看 `modList.txt` 是否包含该 id。**
→ Steam 的两种状态（Subscribed / Enabled）由此天然可得。

### 2.7 模组能力边界

| 内容类型 | 是否可用 |
|---|---|
| 剧本 / 武将 / 头像 / 通用配置 / 技能 Buff / 音频 / 贴图 / 模型 / 多语言 / UGUI 窗口(.pkg) | ✅ |
| FairyGUI UI 包(`UI/*.bytes`) | ❌ `Window.AddPackage` 已注释 |
| C# 热更 DLL / HybridCLR | ❌ `LoadAssembly` 已注释 |
| Lua 脚本 | ❌ 无运行时 Lua 环境 |

→ **模组 = 数据 + 资源，无可执行代码**。好处：安全审核只需扫文件类型与 JSON；而且**能直接解析 zip 内的 JSON 做在线预览**（见 §4.5 内容透视）。

## 3. 产品定位：做一个 Steam 创意工坊

### 3.0 范围界定（沿用已确认口径）

**在范围内（必做）**

| 能力 | 说明 |
|---|---|
| 存储 | 接收并保存模组 zip 包 + 封面图，多版本留存 |
| 分类展示 | 分类 / 标签 / 搜索 / 排序浏览 / Steam 式详情展示 / 分页 |
| 订阅与下载 | Steam 式「订阅」交互 + 状态呈现 + 网页备用下载 + 游戏内协议下载 |
| 创作发布 | 「你的创意工坊」：上传、发版、变更日志、统计 |

**不在范围内（本期不做）**

| 能力 | 原因 |
|---|---|
| 模组加载顺序编排、"整合包"拖拽排序 | 属客户端本地行为；`UIModItem` 上移/下移 + `UIModManager.OnApply` 已有此能力 |
| **Add to Collection 合集** | Steam 的合集是"分享一组物品的清单"，但一旦提供排序 UI 就会被当成加载顺序用；本期先不做，留作决策点 |
| 依赖自动安装 | 只做静态展示与文案提示（等价 Steam 的 Required Items） |
| UGC 后台静默自动更新 | 改为：启动/打开时检查 + 一键更新（避免玩家不知情被改文件） |

**灰区（成本极低，随时可砍）**：好评、浏览数、订阅者数——纯计数，是"最受欢迎榜"的依据。**订阅者数是 Steam 的主指标，建议保留。**

### 3.1 Steam 式状态体系（本设计的核心）

Steam 之所以好用，是因为它永远告诉你"这个东西现在是什么状态"。映射到 Sango：

| 状态 | 判定依据 | 网页 / 游戏内文案 |
|---|---|---|
| 未订阅 Unsubscribed | 本地 `Mods/{id}/` 不存在 | `[ ⬇ 订阅 ]` |
| 订阅中 Subscribing | `mod.isDownloading == true` | `[ 订阅中… 45% ]` |
| 已订阅·最新 Subscribed | 本地存在 且 本地 version == 最新 version | `✓ 已订阅` / `[ 退订 ]` |
| **有更新 Update available** | 本地 version < 最新 version（`Mod.HasNewVersion()`） | `⚠ 有更新 1.1 → 1.2` / `[ 更新 ]` |
| 已订阅·未启用 Subscribed, not enabled | 本地存在 但 不在 `modList.txt` 中 | `✓ 已订阅（未启用）` |
| 你自己的 · 已发布 Published | `mod.authorId == 当前用户` | `[ 管理 ]` |

> 除"订阅中"外，**其余状态均需客户端上报本地安装清单**（见 §5）。这是 Steam 体验唯一要求的新增联动。

### 3.2 三大 Steam 式原则

1. **一次订阅，长期有效**：玩家不用反复来找新版本，客户端会比对版本并提示。
2. **状态永远可见**：任何时刻都知道"装了没 / 要不要更 / 有没有启用"。
3. **创作门槛为零**：游戏内做完武将/剧本 → 一键发布，不用懂目录结构。


### 4.4 你的创意工坊 `/my` （Steam 的 Your files）

- Tab：**已发布**（Published，含统计曲线） / **订阅的** / **关注的作者**
- 已发布列表支持：发新版本（填 Change Notes）、编辑简介标签、上下架、查看 installer 链接

### 4.5 上传页 `/upload`（Steam 的 Publish to Workshop）

拖拽 zip（≤200MB）→ 前端算 sha256（秒传校验）→ 填 Steam 式表单：
名称 / 简介（Markdown）/ 封面（16:9 建议 960×360）/ 类型 / 标签 / 兼容游戏版本 / **Required Items**（填依赖 id）/ 版本 + **Change Notes** → 提交。

### 4.6 特色：内容透视（Content X-Ray）—— 超越 Steam 的能力

因为模组本体是 JSON，**Steam 做不到、本站能做到**：入库时解析 zip 并索引，详情页"▸ 查看内含物品"抽屉里直接展示：

| 面板 | 数据来源 |
|---|---|
| 剧本 | `Scenario/*.json` → 数量、年代、势力数、参战武将数，时间轴呈现 |
| 武将 | `Data/CustomPerson.json` → 数量、五维 TOP10，以**三国风格武将卡**展示 |
| 技能 / Buff | `Data/Skill/*.json` → 新增条目清单 |
| 资源统计 | Face 数 / Sound 数 / pkg 数 / 总文件树 |
| 覆盖提示 | 改写了哪些 `Data/Common/*.json`（未来可做冲突提醒） |

→ 玩家订阅前就能确认"里面到底是不是我想要的 300 个武将"。

### 4.7 分页与性能

- 统一**游标分页**（`cursor + limit`，24 条/批），按 sort_key + id 二级排序，避免深翻页
- 列表只返回精简字段；封面生成 160/320/640 三档 webp，列表用 320
- 索引：`(status, category, sort_key)`、`(author_id)`、`name/description` 全文
- 首页与前几页结果 Redis/LRU 缓存 60s；`mod_list.txt` 结果整体缓存 5 分钟

## 5. 订阅与同步机制（Steam 化必需的新增部分）

### 5.1 为什么必须做

玩家永远在两个地方：网页和游戏。要让网页显示 "✓ 已订阅 / ⚠ 有更新"，**服务端必须知道客户端装了什么**。这是 Steam Workshop 的本质，也是本次设计唯一超出"纯静态展示"的一块——但它仍然是只读+上报，不涉及排序与调度。

### 5.2 同步时序

```
[游戏启动 / 打开模组管理器]
        │
        ├─ 1. 客户端收集本地状态：扫描 Mods/*/mod.info → { id, version }[]
        │     + 读 Mods/modList.txt → enabled[]
        │
        ├─ 2. POST /api/sync/installed  (Bearer Token)
        │     Body: { gameVersion:"1.2", mods:[{id,version,enabled}] }
        │
        ├─ 3. 服务端比对最近版本 → 返回
        │     { updates:[{id,latestVersion,size,changelog}], notice:"…" }
        │
        └─ 4. 客户端：
              · 本地相册 show"N 个模组可更新"红点（照抄 GameVersion 的 window_update 弹窗套路）
              · 用户点[全部更新] → 逐个触发 Mod.Download()
```

- **弱网/离线无感**：上报失败不影响游戏，本地仍可正常玩（服务端上次的记录会保留）。
- **不上报也能用**：网站退化为"不知道你是否订阅"，只显示灰色状态；不影响浏览与下载。
- 上报频率：游戏启动 + 打开模组管理器，两次；不做定时轮询。

### 5.3 网页点「订阅」怎么落地

没有常驻客户端，所以 **Steam 的"网页点了客户端就装"要用两路协同**：

```
网页点 [ ⬇ 订阅 ]
   ├─ POST /api/mods/:id/subscribe      → 记录订阅关系 + 订阅数 +1（即使客户端没起来）
   ├─ 尝试唤起 sango://subscribe/{id}    → 唤起成功：客户端直接下载 + 写启用列表
   └─ 未唤起 → 显示备用方案：
        「已记录订阅。启动游戏后会自动安装」+ [ 复制市场 URL ] + [ 直接下载 zip ]
```

`sango://` 协议由安装器写入 Windows 注册表（无需管理员权限，写 `HKEY_CURRENT_USER\Software\Classes`）。

### 6.1 分发与带宽方案（对象存储 + CDN）—— 轻量服务器必读

**问题**：轻量服务器出口带宽通常仅 3–8 Mbps（≈400 KB/s）。一个 111MB 的头像包需 4.6 分钟，**同时 5 人下载即打满带宽**，且会连带拖垮 API 与网页（共用同一条出口）。轻量机另有月流量包，超额限速或额外计费。

**结论**：**不要升级带宽**——真正吃带宽的只有 zip 与图片，API 全是几 KB 的 JSON。把大文件从这台机器上挪走即可。

**架构**

```
游戏客户端 ──► /market/mod_list.txt      ──► 轻量服务器（JSON，几 KB）   ✅ 零压力
游戏客户端 ──► /mods/{id}@{version}.zip  ──► 302 ──► CDN ──► 回源 COS   ✅ 不走轻量带宽
浏览器     ──► 封面图 / zip               ──► CDN 直连
```

**🎯 客户端零改动（已验证）**

- `GitDownloader.cs:124` 使用 `UnityWebRequest.Get(zipUrl)`，Unity 默认 `redirectLimit = 32`，**自动跟随 302**
- `NetModMarket.MakeUrl()` 拼出的 `{urlBegin}/{id}@{version}.zip` 路径格式**完全不用动**
- → 只需把 §8.5 兼容端点的响应从"直接吐文件"改为 **302 跳 CDN URL**，新旧客户端全部无感
- → **带宽方案可以等有量了再上，不必提前改游戏**

**成本对比**（价格为大致区间，以各家官网实时报价为准）

| 方案 | 成本结构 | 问题 |
|---|---|---|
| 升级轻量带宽 | 固定月费，通常需换机型，数百元/月 | 闲时也烧钱，且上限有限 |
| **对象存储 + CDN** | 存储 ~0.1 元/GB/月 + 流量 ~0.15–0.25 元/GB | 按量付费，无人下载则不花钱 |

50GB 存储 ≈ 5 元/月；1TB 下载 ≈ 150–250 元/月。冷启动期近乎零成本。

**省钱核心：CDN 命中率做到接近 100%**

`{id}@{version}.zip` 是**不可变路径**（某版本内容永不改变），这是天然优势：

```
Cache-Control: public, max-age=31536000, immutable
```

边缘节点缓存一次后全部命中，几乎不回源；封面图用 hash 命名同理。

> ⚠️ **绝对不要**做 `/mods/{id}/latest.zip` 这类可变路径 —— 缓存永远失效，回源流量会把成本打回原形。

**防盗刷三件套（上线前必须配齐）**

1. **CDN 带宽封顶 + 日流量告警**（超上限自动停服，而非产生天价账单）——**优先级第一**
2. **Referer 防盗链** —— 挡住外站直链
3. **单 IP 限速 / UA 过滤** —— CDN 边缘可配

> **不上签名 URL**：客户端拼的是明文 URL（`MakeUrl` 写死），上签名必须改客户端。保持公开读 + 上述三层防护。

**分阶段落地**

| 阶段 | 做法 |
|---|---|
| 冷启动 | 轻量服务器直出 + 单文件上限 50MB；套一层 Cloudflare 免费版挡缓存（国内速度一般，起步够用） |
| 有量后 | 上 COS/OSS + 国内 CDN；`service/storage.ts` 切到对象存储适配器（**已预留**，切换只改配置） |
| 稳定后 | 客户端换 `DownloadHandlerFile`，放开体积上限 |

**⚠️ 客户端侧隐患（同属大文件问题，排进 M5）**

```csharp
// GitDownloader.cs:147
File.WriteAllBytes(tempZipPath, request.downloadHandler.data);
```

`downloadHandler.data` 为 byte[]，**整个 zip 全量驻留内存**，写盘再复制一份 → 200MB 模组峰值内存 400MB+；且**无断点续传**（下到 90% 断开需重头）。
→ 建议改用 `DownloadHandlerFile`（Unity 2018+，流式写盘，内存 O(1)，改动仅 1–2 行）。


## 9. 创作与发布流程

### 9.1 游戏内一键发布（核心场景）

```
[游戏内] 点击「发布到创意工坊」
   ↓ 未登录 → 复用 window_login（CloudSaveClient.Login）→ Token 存 PlayerPrefs
   ↓
window_mod_upload 窗口
   ├─ 内容源：默认 ☑ CustomEdit 目录（可切换：手动选目录 / 已订阅模组改造）
   ├─ 自动扫描：Data/CustomPerson.json → 武将数；Scenario/*.json → 剧本数
   ├─ 表单：名称 / 英文ID / 版本 / Change Notes / 简介 / 类型 / 标签
   ├─ Required Items：下拉勾选本地已装的模组 → 写入 depends
   ├─ 封面：本地图片 或 游戏内头像库选一张（转 jpg，建议 960×360，≤2MB）
   └─ [发布] → 生成 mod.info → 打包 zip → POST /api/mods
   ↓
返回 { id, url } → 「发布成功」+ [在网页查看]（Application.OpenURL）
```

生成的 `mod.info`（由 `ModPacker` 写出）：

```
id=taoge75_wujiang
name=我的自建武将包
description=200名自建武将,含12个剧本
version=1.0
author=taoge75
depends=src_face
poster=poster.jpg
```

zip 布局（**顶层必须是 id 目录**）：

```
taoge75_wujiang@1.0.zip
└─ taoge75_wujiang/
   ├─ mod.info
   ├─ poster.jpg
   ├─ Data/CustomPerson.json      ← 来自 CustomEdit/Data/
   └─ Scenario/Scenario1.json     ← 来自 CustomEdit/Scenario/
```

### 9.2 服务端入库流水线

```
1. 接收 → 白名单校验（.zip，≤200MB）
2. sha256 → 命中则秒传
3. 安全扫描（yauzl 流式遍历，不全量落盘）：
   · 禁止 .dll .exe .so .a .sh .bat .apk / 路径穿越(..) / 绝对路径
   · 单文件 ≤100MB、条目数 ≤20000、压缩比 >200 判为 zip bomb
4. 校验 mod.info：存在 + id 合法(^[A-Za-z0-9_-]+$) + 值中不含 '=' + version 合法
5. 校验 zip 顶层目录名 == id，不符则服务端自动补一层（容错）
6. 内容解析（X-Ray）入 ModContent
7. 封面 → 生成 160/320/640 webp
8. status = pending（可配置可信作者自动过审）
```

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| zip 顶层目录名 ≠ id → 下载后列表不显示 | 高，最难排查 | 入库时服务端自动补齐顶层目录；客户端 `UpdateMod` 增加找不到 `mod.info` 时的递归查找兜底 |
| **两个 `modList.txt`（本地启用清单）与 `mod_list.txt`（市场清单）混淆** | 高，开发期极易出错 | 服务端变量统一命名 `marketIndex` / `enableList`；文档中固定用反引号区分；`sync` 上报字段显式命名 `enabled` |
| 描述含 `=` 被截断 | 中 | 上传拦截 + 生成 `mod.info` 时拒绝 |
| `mod.info` 非 JSON，容易写错 | 中 | 游戏内发布**由程序生成**；网页上传提供校验器 |
| 客户端不联网 / 上报失败 | 中 | 同步失败静默降级，网页状态显示灰色"未知"，不影响浏览下载 |
| 大模组（头像包 100MB+）发布慢/失败 | 高 | 分片上传 + 断点续传 + 秒传（sha256）；游戏内 ≤200MB 并提示 |
| 现有 8080 云存档栈未知 | 中 | 首日确认；同栈合并共用 users 表，异栈则独立部署但共享 Token 密钥与 user 表 |
| 模组启用/顺序调整需重启游戏 | 中 | **网站不介入**（客户端本地行为）；玩家在游戏内 `UIModManager` 调整并重启 |
| 版权风险（搬运原版素材） | 中 | 审核机制 + 举报入口 + 账号绑定 |
| Unity 2021 无内置 WebView | 低 | 详情页走 `Application.OpenURL`；游戏内列表用原生 UGUI（复用 `UIModItem`） |
| **轻量服务器带宽被打满** | **高** | 大文件全部走对象存储 + CDN，API 留在轻量（仅几 KB JSON）；详见 §6.1 |
| **CDN 被盗链导致天价账单** | **高** | 上线前必配：带宽封顶 + 日流量告警 > Referer 防盗链 > 单 IP 限速 |
| 客户端 `downloadHandler.data` 全量驻留内存、无断点续传 | 中 | M5 改用 `DownloadHandlerFile`；在此之前单模组上限 ≤200MB 并提示 |
