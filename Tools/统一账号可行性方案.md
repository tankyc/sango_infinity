# 三站统一账号：可行性方案

> 目标：**武将库**、**云存档**、**创意工坊** 三个站点共用一套账号 —— 注册一次、登录一次，三处通行。
>
> 结论：**可行，且工作量可控**。推荐「以云存档为唯一身份源（IdP），其余两站接入」，分 4 个阶段推进，总计约 **8–13 人天**。真正的成本不在改造，而在**统一域名 + HTTPS** 这个前置条件。

---

## 一、现状盘点

| 维度 | 云存档（`139.155.98.66:8080`） | 武将库（`server/`，端口 3001） | 创意工坊（端口 8081） |
|---|---|---|---|
| 定位 | **游戏账号源**（游戏内登录用它） | 武将数据管理与展示 | 模组发布与订阅 |
| 后端 | 未知（代码不在工作区） | Express | Fastify + Prisma |
| 账号存储 | 未知（推测数据库） | **JSON 文件** `accounts.json` | SQLite `User` 表 |
| 密码散列 | 未知 | scrypt + 随机盐 | bcrypt |
| 令牌 | 未知 | **自研 HMAC-SHA256**（`base64url(payload).signature`），12 小时 | 标准 JWT HS256，30 天 |
| 令牌载荷 | 未知 | `{ u: username, exp }` | `{ uid, username, nickname, role }` |
| 角色模型 | 未知 | guest / editor / admin / super | user / reviewer / admin |
| 注册 | 有 | 有，**默认给 editor（可增删改）** | 有，默认 user |
| 客户端存令牌 | PlayerPrefs（游戏内） | localStorage（推测） | localStorage |

**契约已经对齐的部分**（重要利好）：

- 创意工坊的 `POST /login`、`POST /register`、`GET /me` 是**刻意照着云存档服务做的**（同路径、同 `Bearer` 令牌、同响应形态），源码注释里也写明了「若日后并入现有云存档服务，可直接复用其 users 表」。统一时这一侧几乎不需要动前端。
- 武将库与创意工坊都支持 `Authorization: Bearer`，令牌传递方式一致。

**发现的三个问题**（与本次统一直接相关，建议一并解决）：

1. **武将库「注册即编辑员」**：`REGISTER_ROLE` 默认为 `editor`，任何人自助注册后就能新增 / 修改 / 删除武将数据。这是统一账号后会被放大的风险点，应改为最低权限角色。
2. **武将库账号存在 JSON 文件里**：并发写入没有事务保证，且与另两站的数据库方案不一致；统一后建议整体迁到数据库（或至少改为 IdP 托管）。
3. **三套密码散列算法并存**（未知 / scrypt / bcrypt）：统一后密码应只由 IdP 保管，其余站点不再存密码，这个差异自然消失。

## 二、方案选型

| 路线 | 做法 | 成本 | 主要缺点 |
|---|---|---|---|
| **A. 统一身份源（IdP）** ✭推荐 | 云存档抽出认证能力，作为账号中心；其余两站通过授权码流程接入，各自签发本地会话 | 中（8–13 人天） | 需要改造云存档服务 |
| B. 共享令牌密钥 | 三站使用同一个签名密钥与相同的载荷结构，互相认对方的令牌 | 低–中（3–5 人天） | 任一站改载荷就会连坐；无法做到「一处登出、处处失效」；角色的权威来源不清晰 |
| C. 同域名共享 Cookie | 三站部署在同一域名下的不同路径，靠同域 Cookie 共享登录态 | 低（2–3 人天） | 只解决浏览器场景，**游戏内登录帮不上**；Cookie 方案在跨子域时仍需统一域名 |
| D. 完全合并为一个应用 | 三个站合成一个多模块工程 | 高（20+ 人天） | 改动面最大，收益不比 A 多 |

**推荐 A**，理由：

- 云存档**已经是事实上的游戏账号源**，玩家在游戏里登录用的就是它 —— 让网站去对接它，符合「一个玩家一个身份」的直觉；
- 游戏内登录与网页登录能落到同一账号，这是 B / C 做不到的；
- 各站保留自己的**档案表**（模组作者、武将编辑者等外键都不用动），改造成本可控。

**过渡期可以 B、C 作为补充**：在 A 落地前，先把三站的令牌载荷统一，实现「令牌互认」，能最快看到效果（见阶段 1）。

## 三、推荐架构

```
                    ┌──────────────────────────┐
   游戏内登录 ───────▶│  云存档服务 = 身份源(IdP) │
                    │  账号 / 密码 / 角色(身份) │
                    └──────────┬───────────────┘
                               │ 授权码（服务端到服务端换取）
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
  ┌───────────┐         ┌───────────┐         ┌───────────┐
  │  武将库    │         │  创意工坊  │         │  (未来新站) │
  │ 本地档案表 │         │ 本地档案表 │         │ 本地档案表 │
  │ 本地会话   │         │ 本地会话   │         │ 本地会话   │
  │ 本地权限   │         │ 本地权限   │         │ 本地权限   │
  └───────────┘         └───────────┘         └───────────┘
```

**两条关键设计原则**：

1. **身份统一，权限分散**。IdP 只管「你是谁」（uid、用户名、昵称），**不管「你能干什么」**。武将库的 `editor/admin/super`、创意工坊的 `reviewer/admin` 各站自己维护，互不干涉。否则三套业务权限揉在一起，改一处会牵动三处。
2. **不直接复用 IdP 令牌**。各站用授权码换到用户信息后，**自己签发本地会话令牌**（有效期自定）。这样 IdP 的令牌不会散落到三处的 localStorage 里，登出、吊销、过期策略也能各自掌握。

**登录流程（浏览器）**：

```
① 用户在武将库点「登录」
② 跳转 auth.sangoinf.top/authorize?client=personlib&redirect_uri=https://lib.sangoinf.top/auth/callback&state=<随机>
③ 在统一登录页完成登录（若已有登录态则直接跳过）
④ 回跳 lib.sangoinf.top/auth/callback?code=<一次性码>&state=<校验>
⑤ 武将库后端用 code 向 IdP 换取 { uid, username, nickname }
⑥ 按 uid 找本地档案：有 → 直接发本地会话；无 → 自动建档（JIT provisioning）后发会话
```

**登录流程（游戏内）**：不变。游戏直接打云存档的 `/login`，拿到的令牌继续用于存档接口。网站与游戏共用同一份账号数据，但走各自的登录入口。

## 四、分阶段实施

### 阶段 0：前置条件（必须先做，2–4 人天）

| 项 | 说明 |
|---|---|
| **统一域名** | 用 `sangoinf.top` 规划子域，例如 `auth.`（身份）、`mods.`（创意工坊）、`lib.`（武将库）、`save.`（云存档）。跨站 Cookie、`redirect_uri` 校验、证书都依赖它 |
| **全站 HTTPS** | 目前三处都是 `http://IP:端口`。跨站传递凭证、Cookie 的 `Secure`/`SameSite` 都要求 HTTPS。建议 `certbot` 签发通配符证书 |
| **拿到云存档服务端代码或接口文档** | 需要确认它的令牌格式、角色模型、是否有 `/me`、能否改造（当前代码不在工作区） |
| **数据库就位** | 创意工坊已用 SQLite；建议三站统一到 MySQL（云存档若已是 MySQL 更好） |

### 阶段 1：令牌契约统一（1–2 人天，见效最快）

- 统一载荷字段：`uid`、`username`、`nickname`、`role`、`iat`、`exp`；
- 三站共用同一段「解析并校验令牌」的中间件代码（抽成内部 npm 包或直接复制，后者更省事）；
- 武将库的自研 HMAC 令牌改为标准 JWT（或在网关层做转换）。

完成后，**同一个令牌在三个站点都能通过校验**，能立刻验证「统一账号」的核心假设是否成立，且**不影响任何现有功能**（各站仍可用自己的方式登录）。

### 阶段 2：云存档成为唯一身份源（3–5 人天）

- 云存档侧：抽出独立认证接口 —— `/authorize`、`/token`（授权码换用户信息）、`/me`、`/logout`；
- 武将库侧：账号文件（`accounts.json`）退化为**档案表**，新增 `externalId` 字段（= IdP 的 uid），首次登录自动建档；密码字段清空，登录逻辑改为走 IdP；
- 创意工坊侧：`User` 表同样新增 `externalId`（**外键关系一律不动**，模组作者、评论、订阅都不受影响）；
- 关闭两站的自助注册与本地登录（保留一段时间作为降级通道，见阶段 4）。

### 阶段 3：统一登录体验（2–3 人天）

- 做一个统一登录 / 注册页（放在 `auth.sangoinf.top`），三站共用；
- 各站未登录时跳统一登录页，带 `state` 防 CSRF，回跳校验 `redirect_uri` 白名单；
- 子域之间可选做「一次登录、三站免登」（同域 Cookie 存 IdP 会话）。

### 阶段 4：数据迁移与灰度（1–2 人天）

- **存量账号合并**：按用户名精确匹配 → 绑定；匹配不到的老账号保留本地登录通道，提示用户「请用游戏账号登录后自动绑定」；
- **冲突处理**：同名但不同人时，以游戏账号优先，网站侧账号加后缀保留（不删除数据）；
- **灰度**：两站的本地登录先并行保留 1–2 个版本，观察无异常后再关闭。

## 五、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| IdP 单点故障 | 三站都无法登录 | 各站会话独立有效期（IdP 短暂不可用不影响已登录用户）；IdP 做最小化改造、保持简单 |
| 存量账号无法对应 | 老用户数据割裂 | 双通道并行 + 登录后引导绑定；管理后台提供人工合并 |
| 统一后权限越界 | 例如创意工坊的 admin 拿到武将库的写权限 | **权限模型不统一**（本方案的核心原则）；各站只从 IdP 取身份，角色一律本地判定 |
| 令牌泄漏面变大 | 一处失守波及三处 | 各站签发本地会话、不转发 IdP 令牌；HTTPS + `HttpOnly` Cookie（浏览器侧） |
| 武将库「注册即 editor」 | 统一后风险被放大 | 阶段 2 一并收紧为只读角色，写权限需人工授予 |

## 八、立即可做的最小第一步

如果想先看到效果、又不想动大手术，可以从**创意工坊**入手：

它的登录接口（`/login`、`/register`、`/me`）与云存档是同契约的，因此只需把它的登录流程改为：

1. 收到登录请求后**转发给云存档**（服务端到服务端）；
2. 用返回的 `uid` 在本地 `User` 表按 `externalId` 建档或命中；
3. 签发创意工坊自己的 JWT（保持现有 30 天有效期不变）。

**前端一行都不用改**，就能实现「用游戏账号登录创意工坊」。这一步约 **1 人天**，可以作为整个方案的可行性验证。

## 九、已落地：以创意工坊为账号源（2026-10-03）

> 方向调整：**先不接云存档，直接以创意工坊（ModHub）作为账号源**，武将库接入。
> 云存档的对接留待以后 —— 届时创意工坊可以扮演「身份代理」的角色，把两种来源收敛到一处。

### 实现方式

改造集中在武将库（`Tools/PersonLibraryWeb/`）的**服务端**，前端未改一行：

| 改动点 | 说明 |
|---|---|
| `server/auth.js` | 新增远程身份模块：`remoteLogin` / `remoteRegister` / `ensureAccountForIdentity`；账号结构增加 `externalId` |
| `server/index.js` | `/api/auth/login` 改为「创意工坊优先 → 本站老账号兜底」；`/api/auth/register` 转发给创意工坊 |
| `accounts.json` | 退化为**档案表**：记录显示名、角色、`externalId`；外部身份默认只读 |
| 配置 | `MODHUB_BASE_URL`（默认 `http://127.0.0.1:8081`，同机走回环）、`MODHUB_TIMEOUT_MS` |
| `/api/auth/me` | 增加 `remote` 字段，前端可据此提示账号来源 |

### 两条关键规则

1. **身份统一、权限分散**：创意工坊只回答「你是谁」，武将库的角色（guest / editor / admin / super）**一律以本站为准**。只有对方的 `admin` 映射为本站 `admin`，其余一律 `guest`（只读）—— 否则创意工坊里任何一个注册用户都能改武将数据。
2. **只升不降**：绑定外部身份时，本站已有角色与外部映射角色取**较高者**，老的编辑员账号不会因为绑定而掉权限。

顺带修掉了一个原有隐患：武将库的 `REGISTER_ROLE` 默认是 `editor`（注册即可增删改数据），现在注册走创意工坊、本站建档固定为 `guest`，该问题自然消失。

### 验证结果（12/12 通过）

```
PASS  用创意工坊账号登录武将库                      → user=admin
PASS  创意工坊管理员在武将库拿到写权限（本地原本已是 super 则保持）
PASS  武将库注册走创意工坊                          → 201
PASS  新注册用户在武将库是只读（guest）             → permissions=read
PASS  同一账号可登录创意工坊                        → 证明是同一套账号
PASS  只读用户写数据被拒绝                          → 403
PASS  本站老账号（默认 admin123）仍可登录           → 过渡期双通道
PASS  密码错误返回 401 且提示清晰
PASS  武将库为该身份建了档案 / 清理档案
```

**降级验证**：停掉创意工坊后，武将库登录返回 `503` + `{"message":"账号服务暂时不可用，请稍后再试"}` —— 与「密码错误」区分开，用户不会白白怀疑自己记错了密码。

### 遗留事项

1. **武将库本地的 `admin/admin123` 仍可登录**（过渡期双通道的副作用）。统一完成后建议用 `PUT /api/accounts/admin` 把密码改为一个强密码，或删除该本地账号（改用创意工坊账号登录）。
2. **尚未部署**：以上改动只在本地验证，武将库线上（`3001`）还是旧版本。
3. 可选优化：武将库登录框提示「账号与创意工坊通用」。`/api/auth/me` 已经返回了 `remote` 字段，前端接上即可。
