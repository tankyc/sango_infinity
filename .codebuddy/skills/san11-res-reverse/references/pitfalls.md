# 踩坑全记录（症状 → 错误做法 → 真相 → 正确做法）

按「代价」排序。每条都标了**当初是怎么发现的**，因为下次遇到同样症状时，
真正有用的是那个判据，不是结论本身。

## A. WKMD 模型

### A1. 索引块不能从 `0x60` 读
- 症状：导出的模型是一堆乱插的三角面。
- 错误：`0x60` 看着像「顶点块结束后的第一个块」，就从那儿读 u16 索引。
- 真相：`0x60` 是顶点块结束，中间还夹着「每顶点 4 字节」的附加表（内容全是 `0xFF`）。
- 正确：用段描述块 `+0x28` 的索引块偏移。判据：靠「索引 < 顶点数」过滤后只剩几百个残片 = 读错位置了。

### A2. 索引是三角形条带，不是列表
- 症状：只拿到约 1/3 的面，且绕序交替丢失。
- 错误：按 3 个一组读。
- 正确：u16 条带滑窗展开；重复索引是退化三角形（跳过）；`0xFFFF` 是条带分隔符。
- 判据：2207 从 120 片碎面变成 384 面的完整持剑小人。

### A3. 段数要读 `0x44`
- 症状：「缺面」——护甲、腰带细节整块不见。
- 错误：只解析前两段。
- 真相：1045 赵云身体有 3 段（stride 32/36/44）。

### A4. 法线偏移不是固定 12
- 错误：`+12` 取法线。
- 正确：**法线 = stride − 20，UV = stride − 8**（stride 36 → 法线 16、UV 28；stride 44 → 24 / 36）。

### A5. 条带展开后一半面绕序是反的
- 症状：背面剔除下「缺面」，关掉剔除又「串联」（看到内壁）。
- 真相：文件里这些模型的绕序本来就混着两种方向（1045 翻转率 34%~57%，2207 仅 1%）。
- 正确：展开后逐面比较「面法线 · 顶点法线」，为负就交换两个索引。**顶点法线是权威。**
- 已证实条带解码本身没错：用水杉插件 `mq_import_wkm.dll` 反汇编逐条核对（u16 索引、滑窗、退化跳过、奇偶翻绕序、基址 0）。

### A6. OBJ 的 `f` 索引是全局连续计数
- 症状：内存渲染正常（每段独立数组），回放 OBJ 时第二段起全是竖直碎片柱。
- 正确：多段导出时 `f` 索引必须累加前面段的顶点/UV/法线数量（`o` 组不会重置计数）。

### A7. 整段当一个大条带展开会在组间产生垃圾面
- 症状：脸模型嘴/鼻部位悬浮碎片，且一半面被错误翻转。
- 正确：**按绘制组表逐组切分**，每组独立条带（插件每组一次独立绘制），组间不桥接。
- 组表位置：指针数组在 `0x50 + 段数 × 0x50`；组记录里 `+0x10` 是段号（段归属看它，别按「顶点连续链」猜）。

### A8. 模型自带的骨骼块不是用来摆放的
- 真相：`0x30/0x34` 那份骨骼块是给 `.fcv` 动作用的，导入插件**完全不读**它。
- 摆放用的是 exe 内置的 57 骨骼表（`wkm_bone_table.json`），`W[0]=M[0]`、`W[i]=M[i]·W[parent[i]]`（行向量右乘）。

### A9. 骨骼表三选一是「推断」
- 插件里有三套（San11PK / Female / ChouHi），对应导入对话框的三个文件类型，**由用户选**；
  文件头里没有可识别字段。
- 当前实现按「摆放后与声明包围盒偏差最小」自动选，这是**基于文件自带包围盒的择优，不是文件记录**。
  引用时不要说成「已破解」。

## B. 序列帧（AIMG / 2195 图集）

### B1. 「8 页 256×512 纵向堆叠」只对前 786432 字节成立
后续兵种全错。图集不是规则大图，是**多尺寸子图首尾相接**。

### B2. 「4 页 512×512」字节数同样合法，但连通域宽高比会露馅
```
宽     高      连通域  中位宽  中位高  高/宽
256    4096    886     19.0    24.0    1.26   ← 直立小人（对）
512    2048    1419    19.0    16.0    0.84   ← 每行被劈两半（错）
```
口诀：**小兵必须直立，压扁了就是行宽取错。**

### B3. 别用「行间差异最小」反推行宽
交错伪影的相邻行恰好来自原图同一水平线，反而更像。这个方法会给出错答案。

### B4. 子图起点不在页边界，也不在 2 的幂格子
2203 的块比 256 宽页边界晚 4 像素；2201 的块落在 512 行距的第 341 行。
正确：按 `(atlasOffset, atlasWidth, atlasHeight)` 从像素流重排。

### B5. `(0,0)` 是空槽不是表尾
遇空槽 `break` 导致 2200 只读出 18 组 / 78 帧（真实 42 组 / 228 帧）。
正确：跳过继续读；`index` 保留空洞不重编号。

### B6. `+0` 是累计时间戳，不是帧时长
```
4 帧动作：0.1667 / 0.3333 / 0.5000 / 0.6667   ← 等间隔 1/6 秒
```
每帧时长 = `t[i] − t[i−1]`，首帧 = `t[0]`。早期直接当 duration 用，播放出来一帧比一帧慢。

### B7. 「切出来像小兵」不是验证
密集图集里随便压一块也能切出半张人形（2199 得分 0.179 的候选切出来是一堆残缺马腿，肉眼一瞥像骑兵）。
判据必须用「内区 − 外环 ≥ 0.20」+ 兵种外观两个一起看。

### B8. 得分最高的候选也未必是真解
2202 的最高分候选（0.181）是红衣兵，但它标称蓝色戟兵；真正对得上的是 0.157 那块。

### B9. 有些 aim 的坐标根本不属于这张图集
2197/2198 帧宽中位 24、高 42，而图集里所有直立小兵只有 13~25 像素高，怎么平移都对不上。
遇到这种别再调偏移，先怀疑「它引用的是另一套图集」。

## C. FCVD 动作

### C1. `0x0C/0x0E` 是「总帧数 / 块数」，不是「起始帧 / 结束帧」
早期文档写错了，连带两个脚本按「起始帧」去匹配，结果全是噪声。
判据（两条独立证据）：
- `1121` 头 `+0x0C = 112`，而它最关键帧的帧号是 **111** = 帧数−1；
- `1716` 头 `+0x0C = 31`、`+0x0E = 147`，与运行时动作槽里的 `(21, 31)` 吻合（21 骨骼、31 帧）。

### C2. `块数 ÷ 7` 不是骨骼数
`147 = 21×7` 是「21 骨骼满配」的巧合；大多数文件是 **164 块 / 38 骨骼**（骨号 0..37，平均 4.3 块/骨骼）。
骨骼数 = `max(骨骼号) + 1`。

### C3. 内存里的 fcv 已被重定位
加载后 `0x10` 起的偏移表被替换成**绝对指针数组**，所以「内存里 dump 的头」和「归档文件头」看起来结构不同，
不是文件损坏。块 0 的地址 ≈ `基址 + 0x10 + 块数×4`（有 4 字节对齐差）。

### C4. 帧号是逐分量独立打点
同一骨骼的 x/y/z/w 各自有不同的帧序列，**不要合并**再插值；Unity 端就是 4 条独立曲线。
早期强行合并成统一时间轴，静止骨出现抖动。

### C5. 600 个 fcv 里没有部队动作
全是 `mot_deb`(舌战) / `mot_due`(单挑) / `mot_dip`(外交)。
不要在「部队走路动画」上继续找 —— 归档里没有。想在战场复现只能自己绑骨骼或做程序化。

### C6. 「从某个地址往后数几条」不能当表长（这是本项目最贵的一次误判）
- 症状：在 `0x009CF5F0` 往后看 0x80 字节，正好 5 条 16 字节结构，于是断定「一个角色 5 个动作槽」，
  并推出「`mot_due_b` 6 个文件有 1 个装不进去、`b_000` 被挤掉」。
- 真相：紧邻**前面**（`0x009CF5E0`）还有一条 `mot_due_b_000`，一共 6 条全在。
  这个错判还连累了另一条假佐证 ——「`+0x50` 为 0 ⇒ 5 是上限」，其实那只是这一段就放了 6 条。
- 正确：先扫一段区间看命中分布，用分布定**步长和边界**（`_peek_slots.py --scan`），再谈「表里有什么」。
  实测这张表是「已加载 fcv 表」：268 条、横跨 `0x009CD150`–`0x009CF630`、分 4 个不连续段，
  不按角色分组，同一 fcv 还能有多条副本。
- 通用判据：**一个方向数出 N 条 ≠ 表长 N**。表的边界要靠「两侧都不再命中」来确认。

### C7. 字符串表逆序 ≠ 还有一张顺序表
`.rdata` 里 `mot_due_b_*` 是 `050→000` 逆序存储（定长 40 字节一条，起点 VA `0x75C528`），
而内存表的装表顺序是 `000→050` 正序。这恰好是「存储逆序、使用时正序」的配对，
**不需要再假设中间有一张顺序表**（早期就是这么猜错、并据此去找一张并不存在的表）。

## D. 音频

### D1. KOVS 是异或混淆的 Ogg
`0x20` 起第 i 字节异或 `(i & 0xFF)`。直接搜 `OggS` 搜不到，音乐工具也认不出 —— 这就是「看起来不是音频」的原因。

### D2. 大量音效根本不在 ogg 里
界面/打击/单挑/舌战音效在 13 对 `.whd/.wbd`（裸 PCM）。
`.whd` 描述项 40 字节：`+4` 采样率、`+16` 帧数、`+20` 偏移、`+24` 字节数。
判据：每条「偏移 + 长度」必须**完整覆盖** `.wbd`（100%），否则项解析错了。

### D3. `.whd` magic 低 16 位不是 2D/3D 标记
`0x3200/0x3201` 的含义仍未确定（早期注释写过「3D 标记」，已被证伪）。

## E. exe 与运行时

### E1. `.data` 的 154 MB 几乎全是 0，运行时表静态搜不到
看到「exe 里明明该有个表却搜不到」时，先查它在不在 `0x0089D000`–`0x09C617E0`。
是的话就是运行时才写的：走 `_dbg_probe.py --peek` / `--guard`。

### E2. 地址高低不能判断「堆还是静态」
`0x009CF5F0`、`0x02811E50`、`0x09415A20` 全都在映像内（`.data` 静态池）。
判断必须查段表，不能凭「地址小 = 静态」「地址大 = 堆」。

### E3. capstone 的两个坑
- 从非指令边界起步会**静默错位**（`0x44B600` 解出 `push es`），不报错。
- 默认遇错就停：全段扫描要 `md.skipdata = True`，否则会以为 `.text` 只有 9680 条指令（实际 3.4 MB）。

### E4. 只是想找「谁引用了某个 4 字节常量」时，直接搜字节
`data.find(struct.pack("<I", va))` 比反汇编全段又快又不漏。搜不到再试 `va - 基址` 的相对形式。

### E5. WOW64 下硬件写断点不生效
`Dr0~Dr3` 经 `Wow64SetThreadContext` 写不进去。替代：`PAGE_GUARD`（`--guard`），
或者干脆找上层函数下 `INT3`。

### E6. WOW64 的断点/单步状态码不同
是 `0x4000001F` / `0x4000001E`，不是 `0x80000003` / `0x80000004`。按后者判断会一条都抓不到。

### E7. 断点很容易下在循环体上
`0x0044ABA0` 被当成「动作装载」，实际是骨骼矩阵搬运循环的循环体
（`mov eax,[esi+0x58]` / `shl edx,6` / `add edi,0x28` / `add ebx,0x40`）。
识别方法：命中时寄存器呈等差递增（EDI +0x28、EBX +0x40）= 循环，不是装载。

### E8. 探针不会帮你玩
`_dbg_probe.py` 只负责等目标画面。新拉起游戏后要在 `--timeout` 内手动操作到目标场景，
否则抓到的全是启动噪声（用 `--after N` 跳过前 N 秒）。更省事的是 `--attach` 到已经在那儿的进程。

## F. 工程与流程

### F1. 解析器只有一份
唯一正本是 `d:\sango_infinity_tools\San11Res\`。曾在别处留副本，改了不生效、白查半天。

### F2. 控制台中文乱码不是数据问题
PowerShell 默认代码页导致 `归档` 显示成 `銝剜`。要读中文输出就 `Get-Content -Encoding UTF8`
或让脚本写 UTF-8 文件再读。

### F3. Unity 端 Play 会重载域
静态计数和 `EditorApplication.update` 回调在点 Play 瞬间全丢（「进得去、截不到、也退不出来」）。
待办状态放 `SessionState`，并在 `[InitializeOnLoadMethod]` 里重新挂回调。

### F4. 项目用 URP
只找 `Unlit/Transparent` 会不显示或实心。要先看 `GraphicsSettings.currentRenderPipeline`，
URP 下用 `Universal Render Pipeline/2D/Sprite-Unlit-Default` 并强制透明混合。

### F5. 不要在游戏场景上叠测试对象
加临时角色前先 `NewScene(Single)`，否则游戏相机/对象混进截图，出现莫名白方块。
